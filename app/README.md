# SOMA: Desktop-App

Electron-App (TypeScript) für 3D-Modelle mit einem Coding-Agenten im Terminal. Version **0.10.1** (Major.minor.bugfix, E68, steht in `package.json` und `../python/soma/__init__.py`). Oberfläche nach den Entwürfen in [../design/](../design/), Änderungen in [../CHANGELOG.md](../CHANGELOG.md). Die Kennungen `E12` in Code und Doku verweisen auf das Entscheidungslog der Entwicklung, das nicht im Repo liegt.

## Voraussetzungen

- Node.js 22 oder neuer, Python 3.12 mit CadQuery (Basisumgebung), `soma` darin installiert.
- Entwicklung: `powershell -File ../python/scripts/setup_env.ps1` baut die Basisumgebung aus `python/requirements-base.txt` (mit uv, braucht uv und Python 3.12, E67), installiert `soma` darin editierbar und holt CalculiX mit `python/scripts/fetch_ccx.py` nach `venv\ccx` (E84). Die App findet sie unter `%LOCALAPPDATA%\soma-dev\venv` oder über `SOMA_PYTHON`. Jedes Modell bekommt daneben eine kleine Projektumgebung unter `.soma/env` für Zusatzpakete (E67).
- Hinter einem Proxy lädt Node den Electron-Download nur mit `NODE_USE_ENV_PROXY=1`:
  `NODE_USE_ENV_PROXY=1 node node_modules/electron/install.js` (falls `npm install` das Binary nicht geholt hat).

`npm test` startet die Suiten parallel über `test/run-all.mjs`, längste zuerst. Jede bekommt einen freien Port vom System (`SOMA_TEST_PORT`), damit sich parallele Läufe nicht gegenseitig die App fernsteuern, und gibt ihre Ausgabe am Stück aus, sobald sie fertig ist. Am Ende steht eine Übersicht mit Dauer und Prüfungen je Suite. `animation` und `fem` laufen nur mit `npm run test:all` (`--all`) oder ausdrücklich genannt. `SOMA_TEST_JOBS=1` lässt sie nacheinander laufen, `SOMA_TEST_WATCHDOG_S` setzt den Watchdog je Suite (im Runner 900 s, sonst 360 s), `SOMA_TEST_TIMES=1` schreibt vor jede Prüfung die Sekunden seit Start. Eine einzelne Testdatei direkt (`node test/smoke.mjs`) nimmt Port 9333, wenn `SOMA_TEST_PORT` nicht gesetzt ist.

`SMOKE_VISIBLE=1` zeigt das Fenster. `SMOKE_VISIBLE=offscreen` zeigt es weit außerhalb des Bildschirms ohne Fokus, dann sind Screenshots (`test/versions.png`) frisch. Ein unsichtbares Fenster zeichnet nicht neu, seine Screenshots sind veraltet, die DOM-Prüfungen sind davon nicht betroffen. Mit `SMOKE_VISIBLE=offscreen` und zusätzlich `SMOKE_SHOTS=1` legt der Smoke-Test Bilder der wichtigsten Zustände in `test/shots/` ab (Arbeitsbereich, Code, Dateien, Fehler, Startseite, Agent eingeklappt, Markieren mit Textfeld, leerer Fläche, Auswahl und Farbmenü, dazu das gespeicherte Bild, wie der Agent es sieht), zum Prüfen von Änderungen an der Oberfläche.

**Windows und Netzlaufwerk:** Liegt `node_modules` auf einem Netzlaufwerk, starten die sandboxed Prozesse von Electron nicht (`launch-failed`, Code 18, schwarzes Fenster). `npm start` und der Test nutzen deshalb automatisch eine lokale Kopie von Electron unter `%LOCALAPPDATA%\soma-dev\` (`scripts/electron-local.mjs`, einmalig rund 370 MB). Die App selbst darf auf dem Netzlaufwerk liegen. Eine installierte App muss lokal liegen, sonst zeigt sie eine Fehlermeldung.

## Installationspakete

Jedes Betriebssystem baut sein eigenes Paket, die Python-Basisumgebung, CalculiX und das Git von dugite sind plattformabhängig. Die CI macht das für alle drei Systeme ([../.github/workflows/dist.yml](../.github/workflows/dist.yml), von Hand oder mit einem Tag `vX.Y.Z`, Pakete als Artefakte am Lauf, bei einem Tag zusätzlich als GitHub-Release, solange 0.x als Vorabversion). Lokal:

```
# 1. Python-Basisumgebung: eigenständiges Python 3.12 (python-build-standalone über uv) mit requirements-base.txt, soma und CalculiX
python ../python/scripts/build_runtime.py --target "$LOCALAPPDATA/soma-dev/python-runtime"
# 2. Paket (Windows: NSIS-Installer und ZIP, Linux: AppImage und tar.gz, macOS: dmg für Apple Silicon)
SOMA_RUNTIME="$LOCALAPPDATA/soma-dev/python-runtime" SOMA_RELEASE="$LOCALAPPDATA/soma-dev/release" npm run dist
#    nur den entpackten Ordner (schneller, zum Prüfen): npm run dist:dir
# 3. Smoke-Suite gegen die gepackte App
SOMA_TEST_EXE="$LOCALAPPDATA/soma-dev/release/win-unpacked/SOMA.exe" node test/smoke.mjs
```

- Ohne `--target` und `SOMA_RUNTIME` liegt die Basisumgebung in `app/python-runtime`, die Pakete in `app/release` (beide in `.gitignore`). In einem synchronisierten Ordner (OneDrive, Netzlaufwerk) besser nicht: rund 1,4 GB in Zehntausenden Dateien.
- **Basisumgebung:** Ein venv lässt sich nicht verschieben, deshalb ein eigenständiges Python. Die Startprogramme (`soma`, `pip` …) bekommen einen relativen Pfad zum Python: unter Windows als `.cmd` (PowerShell, cmd) und ohne Endung (Git Bash), sonst als Shell-Vorspann. `build_runtime.py` prüft am Ende eine Kopie in einem Ordner mit Leerzeichen. `EXTERNALLY-MANAGED` bleibt, pip installiert nur in die Projektumgebung (E67).
- **Im Paket:** `resources/python` (Basisumgebung, `paths.ts` findet sie vor der Entwicklungsumgebung), `resources/app` mit `dist/`, `resources/` und nur `dugite` und `node-pty` aus `node_modules` (alles andere bündelt esbuild), ohne asar. Dazu `LICENSE.txt`, `MODEL-EXCEPTION.md` und `THIRD_PARTY_NOTICES.md` (von Hand gepflegt). Die Lizenztexte der npm-Pakete sammelt `esbuild.config.mjs` beim Build nach `dist/licenses/<paket>@<version>/`, weil esbuild sie beim Bündeln verliert.
- **Windows:** Installation für den Nutzer nach `%LOCALAPPDATA%\Programs\SOMA` ohne Adminrechte, unsigniert (SmartScreen warnt beim ersten Start). Dazu `win-unpacked` als ZIP zum Entpacken ohne Installation (nicht das Ziel `portable`, das bei jedem Start nach %TEMP% entpackt). Die App-Daten liegen auch dann unter `%APPDATA%`. Windows überträgt die Download-Markierung (Mark of the Web) beim Entpacken mit dem Explorer auf alle Dateien, ohne „Zulassen“ in den Eigenschaften des ZIPs warnt SmartScreen beim Start von `SOMA.exe` genauso.
- **macOS:** nur Apple Silicon (für Intel fehlt `cryptography` als Wheel), ad-hoc signiert, nicht notarisiert: Gatekeeper lässt die App erst nach Rechtsklick > Öffnen oder `xattr -cr /Applications/SOMA.app` starten. Die installierte App übernimmt beim Start den PATH einer Login-Shell, sonst fänden Agenten-Erkennung und Terminals nichts aus Homebrew oder npm.
- **Linux:** gebaut unter Ubuntu 22.04, braucht glibc 2.31 oder neuer (cadquery-ocp). gmsh braucht libGLU, libXft, libXinerama und libXcursor, `build_runtime.py` liefert sie mit. Ohne nutzbaren Grafiktreiber (VM, Remote-Desktop, xvfb) sperrt Chromium WebGL, bekommt der Viewer deshalb kein WebGL, merkt die App sich das in den App-Daten (`software-gl`) und startet mit `--ignore-gpu-blocklist` neu (Software-Rendering, `main.ts`). Die Tests legen den Merker unter xvfb vorab an (`SOMA_TEST_SOFTWARE_GL=1`). Unter Ubuntu 24.04 und neuer kann AppArmor die Sandbox von Electron im AppImage blockieren.
- Geprüft mit der Smoke-Suite: Windows (lokal und CI), Linux unter WSL mit Ubuntu 24.04 und xvfb, macOS in der CI (dort scheitern nur die Prüfungen mit Koordinaten im Viewer, der Bildschirm des Runners ist zu klein). Auf echten Rechnern kurz ausprobiert (2026-10-11): Linux unter Kubuntu mit Grafikkarte, macOS mit Apple Silicon, beide starten mit 3D-Ansicht.
