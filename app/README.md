# SOMA: Desktop-App

Electron-App (TypeScript) für 3D-Modelle mit einem Coding-Agenten im Terminal. Plan: [../PLAN.md](../PLAN.md). Stand: **Phase 1, Schritte 1 bis 5** (Gerüst, Git und ZIP, Oberfläche nach dem Entwurf in [../design/ui-entwurf.html](../design/ui-entwurf.html), Markierung, Editor), dazu Messen, Gruppen, Schnitt, Skills, Animation, Analyse sowie Bilder und Videos über `soma render`.

## Voraussetzungen

- Node.js 22 oder neuer, Python 3.12 mit CadQuery (Basisumgebung), `soma` darin installiert.
- Entwicklung: die Umgebung aus Phase 0 (`prototype/phase0/setup_env.ps1`) und darin `uv pip install -e ../python`. Die App findet sie unter `%LOCALAPPDATA%\cadide-phase0\venv-full` oder über `SOMA_PYTHON`.
- Hinter einem Proxy lädt Node den Electron-Download nur mit `NODE_USE_ENV_PROXY=1`:
  `NODE_USE_ENV_PROXY=1 node node_modules/electron/install.js` (falls `npm install` das Binary nicht geholt hat).

## Starten und Testen

```
npm install
npm start            # baut und startet
npm run typecheck
npm run test:unit       # Bausteine ohne Electron: Dateien und Ordner nach inputs/, Anlegen, Umbenennen und Papierkorb im Dateibaum, Markierung nach .soma/feedback/, Pfadschutz, Schreiben aus dem Editor mit Konfliktprüfung, App-Icon, Einstellungen, Kategorien, Stufen und Standard der Skills, Abschnitt in AGENTS.md, Animationsdateien bauen nicht das Modell, Zwischenergebnisse nicht in Verlauf und ZIP auch in älteren Projekten (51 Prüfungen)
npm run test:smoke      # echte App, unsichtbar: Projekt, Viewer, Auswahl, Panels, Terminal, Übergabe an den Agenten, Markierung (Zeichnen, Linie, Raster, Auswählen, Verschieben, Drehen, Skalieren, Farben, Bild aus dem Dateibaum), Dateibaum (Markierungen, Menü, Anlegen, Umbenennen, Papierkorb), Auto-Build, Fehlerfall, Export, Ansichtswürfel und Drehpunkt (79 Prüfungen)
npm run test:versions   # Git-Verlauf, Speichern, Öffnen, Vorschau (auch markiert), Wiederherstellen, Störfälle (53 Prüfungen)
npm run test:editor     # Editor: Höhe und Scrollen, Speichern nur auf Wunsch mit genau einem Build (nur bei Python und inputs/), Änderungen des Agenten, Konflikte mit Sicherung, Nur lesen, CRLF, Rückfragen bei Modellwechsel und Reiter schließen, Markdown als Dokument (37 Prüfungen)
npm run test:measure    # Messen: Fläche, Kante, Punkt, Abstand paralleler Ebenen, zweier Bohrungen, zweier Punkte, Punkt zur Ebene, Verdecktes, neuer Build, Vorschau (21 Prüfungen)
npm run test:groups     # Gruppen: eigene und importierte (STEP-Baugruppe), Baum, Aus-/Einblenden und Transparenz je Gruppe, Klick durch transparente Teile, Ausgabe-STEP (17 Prüfungen)
npm run test:section    # Schnitt: X/Y/Z und an Fläche, Eingabe der Lage, Seite wechseln, gefüllte und schraffierte Schnittfläche, Klicks durch den Schnitt, Wandstärke an der Kontur messen, neuer Build (26 Prüfungen)
npm run test:explode    # Explosion: Demontage-Analyse (Richtung je Teil, Schrauben durch ihr Kernloch, Stift schräg aus seiner Bohrung, Baugruppe mit eingeschlossener Mutter, Elternteile), gleiche Lücke, Reihenfolge bei 100 %, Abspielen Schritt für Schritt, Reihenfolge an den Agenten, Auswahl in Einbaulage, Messen setzt zusammen, Schnitt dazu, neuer Build (39 Prüfungen)
npm run test:skills     # Skills: Panel, Stufen Aus/Bei Bedarf/Immer (Kopie mit oder ohne Hinweis, project.json, zwei Listen in AGENTS.md), Einstellungen (Werte in der Kopie, Prüfung, Standard, vorab bei ausgeschaltetem Skill), Ansehen, An Agent geben, Sicherung geänderter Kopien, fehlende Dateien und falsche Listen nur gemeldet, Snapshot und ZIP, Kategorien, Stufen für neue Modelle (47 Prüfungen)
npm run test:fasteners  # Normteile: Maße aus den Tabellen, Lage (at, direction, on, sunk), Bohrungen und Mutternfallen ohne Überschneidung, Einsätze, Fehlermeldungen, Rolle hardware, rotate/translate/moved, Codeblock des Skills „Normteile“, in der App Baum, Auswahl und export --all (37 Prüfungen)
npm run test:animation  # Animation, Analyse, soma render und Video: Bauen über den Watcher, Ablauf als Text, Kollisionsprüfung, Fehler mit Ort, Abspielen im Viewer (Lage, Hervorhebung, Kamera), Ausschluss mit Explosion und Messen, Verbindung mit Schlüssel, Bild, Übersicht, MP4 mit WebVTT, Video abspielen und Standbild markieren, Überhang, Wandstärke, Abstand mit Anzeige und Neu berechnen, Beispiel des Skills, ohne App Grenzwert mit Netzgenauigkeit, Teil vor Gruppe, Problemstellen, bessere Druckrichtung, kurze Schritte als eine Zeile, Modell nur einmal ausgeführt (52 Prüfungen)
node test/run-all.mjs fem  # FEM: Kragbalken gegen die Formel, verschmolzene Teile mit Druck und Eigengewicht, Fehler (Lagerung, Bauteil, Selektor, kein fix, Code), Karte mit Lastfall und Überhöhung, Wert in Ausgangslage, soma render --result, veraltet nach Änderung der Studie, Neu berechnen, Beispiel des Skills (24 Prüfungen)
npm test                # alle zwölf, vier gleichzeitig (test/run-all.mjs)
node test/run-all.mjs smoke editor   # nur diese, nach npm run build
```

`npm test` startet die Suiten parallel über `test/run-all.mjs`, längste zuerst. Jede bekommt einen freien Port vom System (`SOMA_TEST_PORT`), damit sich parallele Läufe nicht gegenseitig die App fernsteuern, und gibt ihre Ausgabe am Stück aus, sobald sie fertig ist. Am Ende steht eine Übersicht mit Dauer und Prüfungen je Suite. `SOMA_TEST_JOBS=1` lässt sie nacheinander laufen, `SOMA_TEST_WATCHDOG_S` setzt den Watchdog je Suite (im Runner 900 s, sonst 360 s), `SOMA_TEST_TIMES=1` schreibt vor jede Prüfung die Sekunden seit Start. Eine einzelne Testdatei direkt (`node test/smoke.mjs`) nimmt Port 9333, wenn `SOMA_TEST_PORT` nicht gesetzt ist.

`SMOKE_VISIBLE=1` zeigt das Fenster. `SMOKE_VISIBLE=offscreen` zeigt es weit außerhalb des Bildschirms ohne Fokus, dann sind Screenshots (`test/versions.png`) frisch. Ein unsichtbares Fenster zeichnet nicht neu, seine Screenshots sind veraltet, die DOM-Prüfungen sind davon nicht betroffen. Mit `SMOKE_VISIBLE=offscreen` und zusätzlich `SMOKE_SHOTS=1` legt der Smoke-Test Bilder der wichtigsten Zustände in `test/shots/` ab (Arbeitsbereich, Code, Dateien, Fehler, Startseite, Agent eingeklappt, Markieren mit Textfeld, leerer Fläche, Auswahl und Farbmenü, dazu das gespeicherte Bild, wie der Agent es sieht), zum Prüfen von Änderungen an der Oberfläche.

**Windows und Netzlaufwerk:** Liegt `node_modules` auf einem Netzlaufwerk, starten die sandboxed Prozesse von Electron nicht (`launch-failed`, Code 18, schwarzes Fenster). `npm start` und der Test nutzen deshalb automatisch eine lokale Kopie von Electron unter `%LOCALAPPDATA%\soma-dev\` (`scripts/electron-local.mjs`, einmalig rund 370 MB). Die App selbst darf auf dem Netzlaufwerk liegen. Eine installierte App muss lokal liegen, sonst zeigt sie eine Fehlermeldung.

## Aufbau

| Pfad | Inhalt |
|---|---|
| `src/main/` | Hauptprozess: `projects.ts` (offenes Projekt, Speichern, Öffnen, Verlauf, Wiederherstellen), `git.ts` (mitgeliefertes Git über dugite), `zip.ts` (ZIP schreiben und sicher entpacken), `workspace.ts` (UUID-Arbeitsordner, Projektzustand doppelt, Projekt-Check nur melden), `build.ts` (Build als Einmal-Prozess mit Entprellung, Warteschlange, Zeitlimit), `measure.ts` (langlebiger Python-Messdienst, `soma serve`), `skills.ts` (Stufen der Skills: Kopie nach `.soma/skills/`, bei Bedarf mit Hinweis, zwei Listen in `AGENTS.md`, Sicherung abweichender Kopien), `dialogs.ts` (native Dialoge, im Test beantwortbar), `watcher.ts`, `terminals.ts` (node-pty, `soma` und `git` im PATH), `files.ts` (Pfadschutz, Dateien nach `inputs/`, Markierungen nach `.soma/feedback/`, Schreiben aus dem Editor mit Konfliktprüfung und Sicherung), `agents.ts`, dazu für E58 `bridge.ts` (Verbindung für `soma render`: HTTP auf 127.0.0.1 mit Schlüssel), `render.ts` (unsichtbares Render-Fenster, Aufträge nacheinander), `animations.ts` (Liste der Animationen und Ergebnisse, Bauen im Hintergrund) |
| `src/preload/` | Schmale, feste Schnittstelle zum Renderer (kein Node-Zugriff dort), `render-preload.ts` für das Render-Fenster |
| `src/renderer/` | Oberfläche: `main.ts` (Verdrahtung: Kopfzeile mit Spalten-Schaltern, Seitenleiste und Code-Spalte, Umschalter oben links im Viewer, Menüs, Auswahl, Export, Übergabe an den Agenten auch per Ziehen ins Terminal, Startseite), `viewer.ts` (three.js, Klick auf Code, Ansichten, Drehpunkt, Schnittebene mit gefüllter Schnittfläche und Kontur, verschobene Bauteile der Explosion mit Wegen, Strahltest der Demontage-Analyse mit BVH aus `three-mesh-bvh`, Vorschaubild, Bild für die Markierung), `viewcube.ts` (Ansichtswürfel in 3D), `sectiontool.ts` (Schnitt: Karte, Ebene, Text für den Agenten), `explodetool.ts` (Explosion: Demontage-Analyse mit Baugruppen und schrägen Richtungen, Elternteile, Lage, Abspielen Schritt für Schritt, Karte, Texte für den Agenten), `skills.ts` (Skills in der Seitenleiste: Zeilen mit Stufen-Schalter, Karte daneben mit Einstellungen), `markup.ts` (Zeichenfläche der Markierung, Formen als bearbeitbare Objekte), `measuretool.ts` (Messen: Ablauf, Karte, Text für den Agenten), `parts.ts` (Bauteilbaum in der Seitenleiste mit Gruppen, Auge und Transparenz, Zeilen lassen sich ins Terminal ziehen), `code.ts` (Code-Spalte mit Editor: CodeMirror 6, Speichern auf Wunsch, Abgleich mit Änderungen des Agenten, Konflikte, Umschalter für Markdown), `markdown.ts` (Markdown als Dokument: Tokens von `marked` direkt als DOM, ohne `innerHTML`), `filetree.ts` (Dateibaum in der Seitenleiste, offene Datei hervorgehoben), `versions.ts` (Verlaufsleiste), `terminals.ts` (xterm.js, Tabs, Einklappen, Einfügen), `ui.ts` (Menüs, Meldungen, Helfer), `icons.ts` (Symbole), `style.css` (Farben mit fester Bedeutung, siehe Kopf der Datei) |
| `src/renderer/` (E58) | `animdata.ts` (Animation aus der glTF-Datei auswerten), `animtool.ts` (Karte „Animation“, gewählt im Umschalter oben links), `overlay.ts` (Untertitel, Beschriftungen, Legende auf einer 2D-Fläche, im Viewer wie im Video), `resultview.ts` und `resulttool.ts` (Ergebnisse farbig, Karte „Analyse“), `videoview.ts` (Video-Player mit Standbild markieren), `render.html` und `render.ts` (unsichtbares Render-Fenster: Bild, Übersicht, MP4 mit WebCodecs und mediabunny) |
| `src/shared/` | `types.ts` Typen des IPC-Vertrags, `editable.ts` welche Dateien der Editor nur zeigt (gilt in Renderer und Hauptprozess) |
| `resources/template/` | Vorlage für neue Projekte: `model.py`, `AGENTS.md`, `CLAUDE.md`, `NOTES.md`, `.gitignore` |
| `resources/skills/` | Mitgelieferte Skills (E17), je eine Markdown-Datei: Kopf mit `title`, `summary`, `topics`, `category` (deutsch, Oberfläche), `name` und `when` (englisch, für `AGENTS.md`: Name und Anlass), `order`, `default:` (Stufe bei neuen Modellen: `always`, `on-demand` oder `off`) und optional Einstellungen als `var name: Standard \| Einheit \| Bezeichnung \| 10..85` oder `\| a, b=Anzeige`, darunter die Regeln für den Agenten auf Englisch mit Platzhaltern `{{name}}` |
| `resources/icon.*` | App-Icon (E44) für Fenster und Taskleiste: `icon.svg` als Vorlage, `icon.ico` (16 bis 256 px) und `icon.png`. Neu erzeugen mit `python scripts/make-icon.py` (braucht Edge und Pillow, kleine Größen bekommen einen dickeren Strich) |
| `../python/soma/` | Hilfsbibliothek und Kommandozeile (`soma build`, `soma export`, `soma glb` für Vorschauen, `soma serve` Messdienst, `measure.py` exakte Werte mit OCC, `fasteners.py` Normteile mit Tabellen aus bd_warehouse in `data/fasteners/`, `anim.py` und `animrun.py` Animationen mit `soma anim`, `analysis.py` Auswertungen mit `soma analyze`, `fem.py` Festigkeit mit `soma analyze fem` (gmsh, pyamg), `render.py` Auftrag an die App für `soma render`, `gltf.py` GLB-Schreiber, `progress.py` Fortschritt langer Befehle) |
| `test/` | `smoke.mjs`, `versions.mjs`, `editor.mjs`, `measure.mjs`, `groups.mjs`, `section.mjs`, `explode.mjs`, `skills.mjs`, `fasteners.mjs`, `animation.mjs` (Ende-zu-Ende), `unit.mjs` (ohne Electron), `harness.mjs` (App starten und steuern), `cdp.mjs` (kleiner DevTools-Client, puppeteer scheitert an Electron 44) |
