# Plan: SOMA (CAD mit KI-Agenten)

> Stand: 2026-09-30 · Status: **Phase 0 abgeschlossen** ([Ergebnisse](prototype/phase0/ERGEBNISSE.md)), **Phase 1 läuft** (Schritte 1 bis 5 erledigt, Messen vorgezogen, siehe Abschnitt 10 und [app/README.md](app/README.md))
> Ursprung: [IDEA.md](IDEA.md) · Begründungen und Historie: [DECISIONS.md](DECISIONS.md)
> Zahlen in Klammern, z. B. (E12), verweisen auf Entscheidungen im Log.

## 1. Vision

Eine Desktop-App, in der ein Nutzer zusammen mit einem KI-Coding-Agenten seiner Wahl (Claude Code, OpenCode, …) 3D-Modelle entwirft. Technisch ist sie eine IDE mit Terminal, Editor und einem eingebauten 3D-Viewer. Sie fühlt sich aber an wie „ein 3D-Modell erstellen und speichern", nicht wie „ein Coding-Projekt starten". Ein Modell ist eine ZIP-Datei, die man frei verschieben kann.

**Abgrenzung zu VS Code:** Modell-Workflow (ZIP, Versions-Schieber), integrierter STEP-Viewer mit Klick auf Code, Screenshot mit Markup als Rückmeldung an den Agenten, feste Projektstruktur, Skills für 3D-Druck und Toleranzen.

**Zielgruppe:** Nicht-Programmierer, die einen eigenen CLI-Agenten mitbringen (E3, E4). **Ziel:** Open Source (E30). **Plattformen:** Windows, macOS, Linux von Anfang an (E2).

## 2. Grundsätze

1. **Kein eigener Harness** (E29). Agenten, Berechtigungen und Schutz vor dem Agenten liegen bei Nutzer und Agent, nicht bei uns. Keine Sandbox.
2. **Agentenunabhängig.** Wir setzen nur auf Dateien, Text und Kommandozeile, nicht auf Eigenheiten einzelner Agenten. Tiefere Integration (MCP) kommt später (E11).
3. **Der Code ist die Wahrheit.** Änderungen am Modell laufen über das Skript. Die App schreibt den Modellcode nicht selbst, sondern übergibt Aufträge an den Agenten (E11, E34).
4. **Eine getestete Umgebung.** Python, CadQuery und Git werden mitgeliefert, kein Bring-your-own (E31, E32).
5. **Robust gegen Abweichungen des Agenten**, siehe Abschnitt 9. Dieser Grundsatz gilt für alle anderen.

## 3. Architektur

```
+---------------------- Electron-App (TypeScript) ----------------------+
| Oberfläche: Panels (Dateien, Code) | 3D-Viewer / Sketch | Agent-Tabs  |
| Hauptprozess: Projekte, ZIP, Git, Dateiüberwachung, Prozessverwaltung |
+-----------+-------------------------------+---------------------------+
            |                               |
   Terminals (xterm.js + node-pty)   Python-Dienst pro Projekt (langlebig)
   Shell im Projektordner,           Modell im Speicher, Build, Mesher,
   Projektumgebung im PATH,          Messungen (OCP/OpenCascade)
   mitgeliefertes git                       |
            |                               |
      CLI-Agent (Claude Code, …)     Paket `soma` (Basisumgebung)
      nutzt `soma build|check|export`  Hilfsbibliothek + CLI
```

- **Desktop:** Electron, TypeScript (E23). Editor: CodeMirror 6 (Phase 1, Schritt 5).
- **Python-Dienst:** Pro Projekt ein langlebiger Prozess für die App (schnelle Messungen, Modell im Speicher). Der Build-Befehl des Agenten läuft zusätzlich als eigenständiger Einmal-Prozess und funktioniert auch ohne App (E24). **Umgesetzt für das Messen** (`soma serve`), gebaut wird weiter im Einmal-Prozess. Damit der Start von Python und der Import von cadquery (rund 3 bis 4 s) nicht bei jedem Build anfallen, hält die App einen vorgewärmten `soma warm` bereit, einen für die ganze App und schon ab dem Start (E66). Was er tun soll (Build, Vorschau eines alten Standes, Export, Animation, Auswertung), erfährt er erst mit einer Auftragszeile. Jeder Auftrag bleibt ein frischer Prozess, ein warmer Build dauert rund 0,5 s statt 4 bis 5 s.
- **CAD-Framework:** **CadQuery**, fest (E12). OpenSCAD ist ausgeschlossen (kein STEP, kein B-Rep).
- **Viewer:** three.js zeigt ein GLB, das nach jedem Build aus der STEP-Datei erzeugt wird (Bauteilnamen, Farben, Flächen- und Kanten-IDs). Exakte Messwerte (Radius, Flächenabstand) fragt die App beim Python-Dienst ab. Es gibt keinen zweiten CAD-Kern im Frontend (E9).

## 4. Projektformat

**Ein Projekt ist eine `.soma`-Datei** (innen eine ZIP, bis E79 hieß sie auch so, ältere `.zip` öffnet die App weiter). Die App arbeitet in einem Arbeitsordner (E21):

- Jedes Projekt hat eine feste **UUID**. Der Arbeitsordner liegt immer unter `<App-Daten>/workspaces/<uuid>/`, nicht im OS-Temp.
- Neue Projekte starten im Arbeitsordner ohne ZIP, bis der Nutzer zum ersten Mal speichert.
- **Speichern nur ausdrücklich**, kein Autosave in die ZIP. Dazu Absturz-Wiederherstellung.
- **Öffnen:** Existiert der Arbeitsordner nicht, wird die ZIP entpackt. Existiert er mit ungespeicherten Änderungen oder Abweichungen, **fragt die App nach** (wiederherstellen oder ZIP laden).
- Der stabile Pfad hält die **Agenten-Chats auf demselben Rechner** erhalten. Auf einem anderen Rechner gehen sie verloren, das ist bewusst akzeptiert (E5).

**Ordnerstruktur (E26)**

```
<projekt>/
├── AGENTS.md          app-verwaltet: Regeln, Konventionen, Skill-Liste, Git-Regeln, Befehle
├── CLAUDE.md          Verweis auf AGENTS.md (für Claude Code)
├── NOTES.md           Nutzer/Agent, wird nie überschrieben (Arbeitsname)
├── requirements.txt   Zusatzpakete, die das Modell importiert, mit Version, von `soma build` gepflegt (E67)
├── parameters.json    Werte des Nutzers aus dem Parameter-Panel, gelten vor denen aus param() im Code (E74)
├── model.py           fester Einstiegspunkt
├── parts/             Bauteile (optional)
├── inputs/            mitgebrachte Dateien (z. B. STEP), Drag-and-drop im Dateien-Tab
├── output/
│   └── model.step     Hauptergebnis mit allen Bauteilen, benannt, farbig
├── exports/           Einzelexporte (Ort noch nicht festgelegt)
├── animations/        Animationen in Python (optional, E58)
├── renders/           Bilder und Videos von soma render (nicht in Git und ZIP, E58, E75)
├── .soma/
│   ├── project.json   ID, App-Version (`app_version`, zuletzt gespeichert mit, E68), api_version, Stufen der Skills, Hauptdatei
│   ├── skills/        eingeschaltete Skills (Bei Bedarf, Immer) als Markdown
│   ├── feedback/      Screenshots und Skizzen (nicht in Git)
│   ├── anim/, results/  gebaute Animationen und Ergebnisse von soma analyze (nicht in Git, E58)
│   ├── env/           Projektumgebung für Zusatzpakete (nicht in Git und ZIP, E67)
│   ├── model.map.json und GLB-Cache (nicht in Git)
└── .git/  .gitignore
```

Einfacher Fall: alles steht in `model.py`. Bei wachsender Komplexität lagert der Agent Bauteile nach `parts/` aus (E6).

**Git (E7, E8, E35)**

- Jedes Projekt bekommt ein Git-Repo, das in der ZIP mitwandert. Das Git-Binary wird mitgeliefert (E31).
- Der **Agent committet selbst** nach sinnvollen Iterationen (Anweisung in `AGENTS.md`). Beim Speichern legt die App verbliebene Änderungen als **Auto-Snapshot** an.
- **Getrackt:** Skripte, `inputs/`, `output/model.step`, `requirements.txt`, `parameters.json`, `project.json`, `skills/`. **Nicht getrackt:** GLB-Cache, Mapping, `feedback/`, `renders/`, `.soma/anim/`, `.soma/results/` (entstehen aus dem Code neu, wandern aber mit der ZIP) und die Projektumgebung `.soma/env/` (auch nicht in der ZIP, E67).
- **Umsetzung und Befund:** Die App nutzt das mitgelieferte Git (dugite, Git 2.53, rund 115 MB) und stellt es auch den Terminals vorn im PATH bereit. **STEP-Dateien sind nicht byte-stabil** (jeder Build ändert den Zeitstempel, manchmal die Reihenfolge einzelner Zeilen). Deshalb zählt `output/` nicht als ungespeicherte Änderung, wird aber mitcommittet, damit alte Stände als Vorschau anzeigbar bleiben. Der Startcommit entsteht nach einem ersten Build und enthält bereits eine STEP.
- **Versions-Schieber:** Leiste unter dem Viewer, Commits als Punkte, letzter Punkt ist der aktuelle Arbeitsstand. Alte Stände sind **Vorschau** (STEP per `git show`, Arbeitsordner bleibt unberührt). Der Knopf **„Stand wiederherstellen"** kopiert die Dateien und legt einen **neuen Commit** an. Es gibt keinen Checkout oder Reset und keine Branches.

**Projektzustand (E27):** ID und Einstellungen liegen doppelt: in `.soma/project.json` (ZIP) und als Kopie in den App-Daten. Bei Verlust dient die jeweils andere Quelle als Rückfall.

## 5. Hilfsbibliothek und Befehle (`soma`)

Das Paket `soma` liegt in der mitgelieferten **Basisumgebung**, nicht im Projekt. Neue App-Versionen bringen es mit, alte Projekte profitieren von Fixes. `api_version` in `project.json` sichert die Abwärtskompatibilität (E36). Paket und Befehl heißen `soma` (E43).

| Baustein | Aufgabe |
|---|---|
| `add_part("Deckel", obj, role=...)` | Bauteil registrieren (verbindlich, E10). Merkt sich Datei und Zeile, schreibt Namen und Farbe in den STEP-Baum, Positionen und Anzeigename in `model.map.json`. **Namen in der STEP nur ASCII** (Umlaute werden umgeschrieben, sonst zerstört der Export sie), Namen müssen eindeutig sein. Rolle `reference` ist eine Markierung (halbtransparent, eigener Ast, nicht in `--all`), Rolle `hardware` ein Zukaufteil (deckend, in der STEP bei seiner Gruppe, nicht in `--all`, E48) |
| `param(38.0, "Bohrung", min=30, max=42, unit="mm")` | Wert, den der Nutzer im Parameter-Panel ändern darf (E74). Liefert den Wert des Nutzers aus `parameters.json`, sonst den aus dem Code. Die Art folgt aus dem Wert (Zahl, ganze Zahl, Schalter, Text) oder `options=`, dazu `step`, `unit`, `group`, `help`. Fehler im Aufruf brechen den Build mit Zeile ab. `soma build` nennt die Werte des Nutzers und meldet Werte außerhalb des Bereichs, unpassende und solche ohne Parameter |
| `soma.fasteners` | Normteile (E48): `Screw`, `Nut`, `Washer`, `HeatSetInsert` ohne Gewinde, mit Maßen aus den Tabellen von bd_warehouse, Lage über Auflagepunkt und Richtung, passende Bohrungen als Werkzeuge für `cut()` |
| `soma build` | Baut STEP, GLB und Mapping in einem Lauf. Gemeinsam für App und Agent. Führt vorab einen kurzen Check aus und gibt Warnungen mit aus (E20) |
| `soma check` | Prüft die Projektstruktur und **meldet nur**, mit konkreten Handlungshinweisen, auch maschinenlesbar. Kein `--fix`. Der Agent repariert nach eigenem Ermessen (E28) |
| `soma export <Bauteil\|--all> --format …` | Einzelexport auf Basis der registrierten Bauteile, auch per Kontextmenü im Tree. Formate (in Phase 0 geprüft): STEP, STL, 3MF, AMF, BREP, IGES, OBJ, VRML, GLB/GLTF. 2D: DXF (Schnitt), SVG (Projektion) (E34) |
| `soma.anim` | Animationen in `animations/*.py` (E58): `Animation("Name")`, Gelenke `hinge`, `slider`, `part`, Zeitleiste `play`, `wait`, `title`, Kamera `set`, `move`, `orbit`, `zoom`, Texte `caption`, `label`, Zustände `highlight`, `hide`, `show`, `ghost` |
| `soma anim build \| list \| info \| check` | Animationen bauen (glTF nach `.soma/anim/`), auflisten, als Text beschreiben, auf Überschneidung und Mindestabstand prüfen (E58) |
| `soma analyze overhang \| thickness \| clearance` | Wert an jeder Stelle der Oberfläche, Zusammenfassung je Bauteil, Ergebnis nach `.soma/results/` (E58) |
| `soma analyze fem analyses/<x>.py` | Festigkeit mit FEM: Lastfall als Python-Datei, Sicherheit, Spannung und Verschiebung je Stelle, Ergebnis nach `.soma/results/` (E65) |
| `soma render` | Bild, Übersicht oder Video über die App nach `renders/` (E58). Nur in den Terminals der App |
| `soma drawing build \| list \| info` | Technische Zeichnungen aus `drawings/*.py` (`soma.drawing`) als PDF und DXF nach `output/drawings/`, dazu ein Bild zum Prüfen, Hinweise der Prüfung mit Zeile (E76) |

**Bauen (E20):** Auto-Build bei Änderung von `model.py` und `parts/` (Hintergrund, Debounce, abbrechbar). Er ist **abschaltbar**, weil große Modelle sonst die App bremsen. Dann baut der Nutzer per Knopf oder der Agent per Befehl.

**Pakete (E25, E67):** Zusatzpakete sind der Sonderfall. Die Basisumgebung bleibt unverändert. Jedes Projekt hat eine eigene kleine Umgebung im Arbeitsordner (`.soma/env`, nicht in der ZIP), die die Basis mitbenutzt. Der Agent tippt nur `pip install <paket>`, die Terminals leiten pip dorthin. `soma build` trägt die Pakete, die das Modell importiert, in `requirements.txt` ein. Auf einem anderen Rechner installiert die App sie vor dem ersten Build. Umsetzung in Abschnitt 10.

## 6. Agenten-Anbindung

- **Terminal (E19):** Freies Terminal mit mehreren Tabs im Projektordner. Startbuttons für erkannte Agenten. Der zuletzt benutzte Agent startet beim Öffnen automatisch, **ohne Resume**. Der Nutzer installiert den Agenten selbst, die App hilft mit Erkennung und Hinweisen (E4).
- **`AGENTS.md` (E18):** Ganz app-verwaltet, Notizen stehen getrennt in `NOTES.md`. Beim Öffnen eines Projekts mit älterer Regelversion wird sie erneuert, dem Nutzer angezeigt und als Commit gesichert (E36). Der Verweis auf die Notizen steht ganz oben.
- **Skills (E17, E55):** Markdown-Regeln (z. B. 3D-Druck, Toleranzen, CNC-Fräsen), je Modell in drei Stufen: Aus, Bei Bedarf (der Agent liest sie, wenn das Thema aufkommt) und Immer. Eingeschaltete Skills liegen in `.soma/skills/` und stehen mit vollem Pfad in `AGENTS.md`, „Bei Bedarf“ mit Anlass. Mitgelieferte und eigene des Nutzers, angelegt und geändert in den Einstellungen (E78).
- **Rückmeldung an den Agenten (E11):** Markierungen (Viewer-Bild oder leere Fläche mit Zeichnung) landen als PNG in `.soma/feedback/`, Auswahlen (Bauteilname, Datei, Zeilen, Fläche) und Build-Fehler gehen als Text. Die App fügt Pfad oder Text in die Eingabezeile des Terminals ein, der Nutzer schickt selbst ab. Später kommt ein MCP-Server der App dazu.
- **Bilder und Videos für den Agenten (E58):** `soma render` schickt den Auftrag über eine lokale Verbindung an die App (HTTP nur auf 127.0.0.1, freier Port, Schlüssel je App-Start, beides als `SOMA_APP` und `SOMA_APP_TOKEN` in den Terminals der App). Ein unsichtbares Fenster rendert mit demselben Viewer, der Agent öffnet die PNG-Dateien. Videos kann er nicht ansehen, zu jedem Video entsteht deshalb eine Übersicht mit Standbildern und Zeiten. Dieselbe Verbindung kann später den MCP-Server tragen.

## 7. Oberfläche und Viewer

**Layout (E15, E38, E62, Entwurf in [design/ui-entwurf-2.html](design/ui-entwurf-2.html), Vorgänger [design/ui-entwurf.html](design/ui-entwurf.html)):** Das Modell ist die Hauptsache, der Viewer bekommt die größte Fläche. Von links nach rechts: eine schmale **Leiste** wählt, was die **Seitenleiste** zeigt (*Bauteile*, *Parameter* (E74), *Dateien*, *Skills*, eine Ansicht zur Zeit), daneben bei Bedarf der **Code** als eigene Spalte, dann der **Viewer** mit der **Verlaufsleiste** darunter, rechts der **Agent-Bereich** mit Tabs. **Schalter oben rechts** blenden Seitenleiste, Code und Agent unabhängig ein und aus (Strg 1, 2, 3). Im Viewer hat jeder Ort eine Frage: oben links der **Umschalter** „Modell ▾“ (was zu sehen ist: das Modell, eine Analyse, eine Animation oder ein Video), oben in der Mitte die **Werkzeuge** (Messen, Schnitt, Explosion, Markieren), oben rechts der **Ansichtswürfel** mit Einpassen, Standardansicht und Darstellung, unten links die **Karten** (Auswahl, Werkzeug, Ergebnis). „An Agent geben“ steht in der Karte, um die es geht, Bauteile und Dateien lassen sich auch ins Terminal ziehen. Die **Kopfzeile** zeigt Zustände: Modellname als Dokumentmenü, Speicherstand, Build-Anzeige mit Auto-Build, die Spalten-Schalter, dazu Exportieren und Speichern. Eine Startseite zeigt Modelle, erkannte Agenten und den Hinweis auf die Rechte des Agenten.

**Viewer (E22, E33):**

| Phase | Funktionen |
|---|---|
| **Phase 1 (MVP)** | Navigation, Standardansichten, Darstellungsmodi (schattiert, Kanten, Drahtgitter, Transparenz), Ein-/Ausblenden über den Tree, Klick auf Bauteil → Codezeile, **Screenshot mit Markup** |
| **Danach** | Messen (Punkt-zu-Punkt, Bounding-Box, exakte Werte, **umgesetzt**), Schnittansicht (wichtig für Gehäuse, **umgesetzt**), Versions-Schieber (umgesetzt in Schritt 2), Explosionsansicht (mit Demontage-Analyse **umgesetzt**, E56, E57, E59) |
| **Später** | Volumen/Gewicht, Versionsvergleich |

Der Viewer zeigt auch **beliebige weitere STEP-Dateien** im Basismodus, ohne Mapping und Zusatzfunktionen. Standardanzeige ist immer das Hauptmodell.

**2D-Sketching (E16):** Nur Bild-Markup ohne Maßhaltigkeit auf Viewer-Screenshots und leerer Fläche (Freihand, Formen, Pfeile, Text). Ergebnis ist ein PNG. Kein Constraint-Sketcher. Umgesetzt in Phase 1, Schritt 4 (Abschnitt 10).

**Animation, Analyse und Video (E58, E62):** Ergebnisse des Agenten, im Umschalter oben links im Viewer wählbar, Videos spielen über dem Viewer. Umgesetzt, siehe Abschnitt 10.

**Nächster Umbau (E82, Entwurf in [design/strukturbaum-entwurf.html](design/strukturbaum-entwurf.html), noch nicht umgesetzt):** Die Leiste zeigt Parameters und Files, dann Analysis und Animation, dann Skills, getrennt durch Striche. Der Reiter Bauteile und der Umschalter oben links entfallen. Die Bauteile stehen als Strukturbaum ohne Hintergrund ganz oben links im Viewer, eingeklappt nur der Name des Modells, aufgeklappt mit Baumstrichen und direkt vor jedem Namen Auge (ausblenden) und Halbkreis (transparent). Derselbe Baum gilt in Modell, Analyse und Animation. Die Reiter Analysis und Animation zeigen Liste und Bericht, das × rechts in der Leiste unten im Bild führt zurück zum Modell.

**Dateien im Code-Panel:** Python und Text im Editor, Markdown als Dokument (E51), PDF (E54) und DXF (E80) in eigenen Ansichten nur zum Lesen. Bilder öffnen auf der Zeichenfläche der Markierung (E52), Videos über dem Viewer.

## 9. Robustheit gegen Abweichungen des Agenten

Agenten befolgen `AGENTS.md` nicht zuverlässig. Sie können Dateien verschieben oder löschen, eigene Umgebungen (z. B. `.venv`) anlegen, `AGENTS.md` ändern, Git umbauen oder an der App vorbei arbeiten. **Die App darf dadurch nicht kaputtgehen.**

**Regeln (Entwurf, noch nicht ausdrücklich bestätigt)**

1. **Der Arbeitsordner ist nicht vertrauenswürdig.** `AGENTS.md` ist eine Bitte, keine Garantie.
2. **Jede Konvention braucht einen Rückfallweg.** Ohne Hilfsbibliothek zeigt der Viewer trotzdem die STEP-Datei, ohne Klick→Code.
3. **Erkennen und erklären statt abstürzen.** Der **Projekt-Check** läuft beim Öffnen, Bauen und Speichern. Keine automatischen Reparaturen, kein Reparieren-Button (E28).
4. **App-kritischer Zustand ist aus einer zweiten Quelle wiederherstellbar** (E27).
5. **Nichts wird stillschweigend überschrieben oder zerstört.** Wo die App doch eingreift, gibt es vorher Backup oder Git-Stand und einen Hinweis.

**Störfälle** (Reaktionen sind Richtungen, keine fertigen Spezifikationen)

| Störfall | Mögliche Folge | Richtung |
|---|---|---|
| `model.py` fehlt, umbenannt oder verschoben | Kein Build | Einstiegspunkt in `project.json` wählbar, Hinweis |
| Agent exportiert selbst oder ohne Hilfsbibliothek | Kein Mapping/GLB | STEP-Fallback im Viewer, Hinweis |
| Mehrere oder anders benannte STEP-Dateien | Unklar, was angezeigt wird | Hauptausgabe in `project.json`, sonst Auswahlliste |
| Agent legt `.venv` an und installiert dort | Build findet Pakete nicht, `.venv` landet in ZIP/Git | **Umgesetzt:** `.venv`/`venv`/`env` nie in ZIP, Dateibaum und Watcher, der Projekt-Check meldet sie. `AGENTS.md` verbietet sie (E67) |
| Agent nutzt anderes Python oder `pip --user` | Paketliste unvollständig | **Umgesetzt (E67):** Jedes `pip` im Terminal installiert über `PIP_PYTHON` in die Projektumgebung, `--user` lehnt pip dort ab. Ein Python mit vollem Pfad am Terminal vorbei bleibt möglich, der Build scheitert dann am Import |
| Agent will ein Paket, das eine andere Version eines Basispakets braucht (z. B. `numpy<2`) | CadQuery oder OCP liefen nicht mehr | **Umgesetzt (E67):** Die Versionen der Basis sind in der `pip.ini` der Projektumgebung festgelegt, pip lehnt mit klarer Meldung ab |
| `AGENTS.md` verändert oder gelöscht | Regeln fehlen | Prüfsumme, im Check melden. Erneuerung nur beim Versions-Update (E36) |
| `.soma/` oder `project.json` gelöscht | ID und Einstellungen weg | Aus App-Daten bzw. ZIP wiederherstellen (siehe offene Punkte) |
| `.git` gelöscht, neu initialisiert, History umgeschrieben, anderer Branch | Zeitleiste kaputt | Zeitleiste tolerant aus `git log`, Bruch im Check melden |
| Agent committet nie oder zu oft, riesige Dateien | Leerer Schieber, große ZIP | Auto-Snapshot, Größenwarnung |
| `inputs/` verändert | Mitgebrachte Datei verfälscht | Git-Stand, Hinweis |
| Build hängt oder dauert endlos | App blockiert | Timeout, Abbrechen, Dienst neu starten |
| Agent arbeitet außerhalb des Projektordners | Ergebnisse fehlen in der ZIP | Nicht verhinderbar, wo möglich erkennen |
| Agent ändert eine Datei, die der Nutzer gerade im Editor bearbeitet | Eine der beiden Fassungen ginge verloren | **Umgesetzt:** nichts überschreiben, Hinweis im Editor, der Nutzer wählt, die andere Fassung kommt in eine Sicherung |
| Python-Dienst stürzt ab | Viewer/Messen tot | Automatischer Neustart, Meldung |

## 10. Phasen

**Phase 0: technischer Prototyp ohne App (E13, E14). Abgeschlossen**, alle Punkte bestanden. Details und Zahlen in [ERGEBNISSE.md](prototype/phase0/ERGEBNISSE.md), Code und Tests in `prototype/phase0/`:

1. **STEP mit Namen und Farben:** `cq.Assembly.export` genügt, kein eigener XCAF-Export nötig. Nicht-ASCII-Namen werden beim Export zerstört, daher ASCII-Namen in der STEP.
2. **GLB mit Flächen-IDs:** eigener Mesher (rund 150 Zeilen), alle IDs gegen OCC verifiziert. Die IDs gelten nur für einen Build. Der Python-Anteil ist nicht der Engpass, das Meshen in OCC ist es.
3. **Klick → Datei und Zeile:** in echtem Browser bestanden, auf Ebene von Bauteil und Fläche. Verknüpft wird der `add_part`-Aufruf mit Zeilenbereich.
4. **Fremd-STEP, Messen, Aussparung, Referenz:** bestanden, Abstände und Radien exakt über die IDs. Der Basismodus für fremde STEP-Dateien funktioniert. Getestet nur mit synthetischer Platine.
5. **Umgebung:** VTK lässt sich nicht entfernen (OCP hängt hart daran). Installiert 0,76 bis 1,04 GB, vorerst hingenommen (E37).
6. **Exportformate:** 12 Formate, PLY und X_T entfallen.

*Messen (vorgezogen aus „Danach“, E9, E22, E24; 23 Prüfungen in `app/test/measure.mjs`):*

- **Ablauf:** „Messen“ im Viewer schaltet den Messmodus. Ein Klick wählt einen Eckpunkt, eine Kante oder eine Fläche, in dieser Reihenfolge (Punkte mit 9 px Fangradius, Kanten mit 7 px, Verdecktes zählt nicht), und zeigt die exakten Werte: Lage eines Punkts, Durchmesser und Radius (Zylinder, Kreis, Kugel), Achse oder Normale, Länge, Flächeninhalt, dazu die Außenmaße des Bauteils. Ein zweiter Klick misst zum ersten: Abstand paralleler Ebenen (Wandstärke, Spaltmaß), Abstand der Achsen oder Mittelpunkte (Bohrungen), vom Punkt aus den Abstand zur Ebene, Achse oder Geraden, zwischen zwei Punkten ihren Abstand, sonst den kürzesten Abstand, dazu Punkt zu Punkt mit ΔX/ΔY/ΔZ und den Winkel. Punkte kamen auf Wunsch des Nutzers dazu, der Mesher legt dafür eine Tabelle der Eckpunkte mit exakten Koordinaten ins GLB. Ein langlebiger Python-Dienst (`soma serve`, JSON-Zeilen) startet beim Einschalten des Messmodus und lädt den Stand gleich vorab (`prepare`, bei großen Baugruppen Sekunden), nach einem neuen Build erneut. Die Messkarte zeigt dabei „Messdienst startet …“ bzw. „Geometrie wird geladen (N Bauteile) …“ mit Sekunden und laufendem Balken. Klicks gehen schon, ihre Messung wartet auf das Laden. *Schnitt (vorgezogen aus „Danach“, Wunsch des Nutzers; 26 Prüfungen in `app/test/section.mjs`):*

- **Ablauf:** „Schnitt“ im Viewer öffnet die Karte unten rechts. Die Ebene steht senkrecht zu X, Y oder Z, zuerst mitten im Modell. Weggeschnitten wird die Seite, von der die Standardansicht kommt (rechts, vorne, oben), so sieht man gleich hinein. „Seite wechseln“ dreht das um, „Blick auf den Schnitt“ dreht die Kamera senkrecht auf die Ebene. Die Lage stellt ein Schieber ein oder ein Eingabefeld in mm (Komma oder Punkt, Enter übernimmt, Pfeiltasten 1 mm, mit Umschalt 10 mm, mit Alt 0,1 mm).
- **An einer Fläche ausrichten:** „Fläche“ und dann eine ebene Fläche anklicken: Die Ebene liegt parallel dazu, anfangs mitten durch das Bauteil der Fläche, eingestellt wird die Tiefe ab der Fläche. Unter dem Zeiger leuchtet die Fläche auf, eine gekrümmte wird abgelehnt, Escape bricht ab.
- **Darstellung:** Die Schnittfläche ist gefüllt, je Bauteil in seiner Farbe (abgedunkelt) und schraffiert, die Richtung der Schraffur wechselt von Bauteil zu Bauteil. Eine dunkle Kontur umrandet sie. Gefüllt werden nur sichtbare, deckende, geschlossene Körper (der Mesher schreibt dafür `solid` ins GLB), bei transparent geschalteten Teilen und Referenzen sieht man ohnehin hinein. Kanten, Hervorhebungen und Messmarken der Elemente werden mitgeschnitten, Messstrecken nicht. Das Vorschaubild der Startseite zeigt das Modell ohne Schnitt.
- **Klicks und Messen:** Was weggeschnitten ist, lässt sich nicht anklicken, der Klick geht dorthin, wo man hinsieht. Ein Klick auf die Schnittfläche wählt das Bauteil („Schnittfläche · ganzes Bauteil“), Doppelklick setzt dort den Drehpunkt. Beim Messen wählt ein Klick nahe der Kontur die geschnittene Fläche, so misst man Wandstärken direkt im Schnitt (zwei Konturlinien ergeben den Abstand der Ebenen). Die Schnittfläche selbst hat keine exakte Geometrie, ein Klick darauf gibt nur einen Hinweis und verwirft die Messung nicht.
- **Für den Agenten:** Eine Markierung im Schnitt nennt die Ebene und die weggeschnittene Seite (`Schnittansicht bei X = 0.000 mm, weggeschnitten ist X > 0.000`), sonst hielte der Agent die Schnittfläche für eine echte Fläche.
- Der Schnitt ändert nichts am Modell, bleibt über neue Builds und Vorschauen erhalten und wird nicht gespeichert.
- **Technik:** eine Schnittebene von three.js für alle betroffenen Materialien, die Füllung über den Schablonenpuffer (Rückseiten zählen hoch, Vorderseiten herunter, wo etwas übrig bleibt, zeichnet eine Platte in der Ebene), die Kontur aus den Dreiecken des Netzes.
- **Nebenbei behoben:** Ein nur lesbarer Reiter im Editor, dessen Datei gelöscht wurde, galt als Konflikt und blockierte das Speichern des Modells. Er schließt sich jetzt. Ein Konflikt erledigt sich auch, wenn die Datei wieder so ist wie zuletzt gelesen.

*Explosion (vorgezogen aus „Später“, Wunsch des Nutzers, E56, E57, E59, E60; 50 Prüfungen in `app/test/explode.mjs`, dazu am Motormodell des Nutzers gesichtet):*

- **Ablauf:** „Explosion“ im Viewer öffnet die Karte unten rechts, die Bauteile gleiten auf 50 % auseinander. Der Schieber stellt den Abstand ein: bis 50 % gleiten die Teile aus der Einbaulage in die Explosion, darüber wird die Lücke bis aufs Dreifache größer. Richtungsknöpfe gibt es nicht (E61): Ist ein Teil in mehrere Richtungen frei, bevorzugt die Analyse die Achse der meisten Normteile, ohne Normteile die, entlang der Teile aufeinanderliegen, sonst Z. „Wege“ zeigt gestrichelt den eigenen Weg jedes Teils (ab seinem Elternteil), „Einpassen“ holt das größere Modell ins Bild. Schließen setzt das Modell gleitend wieder zusammen.
- **Demontage-Analyse (per Skript ohne KI, E59):** Ein Strahltest im Viewer bestimmt, was jedem Teil in welcher Richtung im Weg steht. Er schießt von bis zu 600 Punkten knapp unter der Oberfläche jedes Teils Strahlen in alle Kandidatenrichtungen (±X, ±Y, ±Z und die Achsen der Normteile), gegen alle Teile zugleich (BVH aus `three-mesh-bvh`, MIT). Ein Strahl liefert beides: wen das Teil trifft und wer in der Gegenrichtung gegen das Teil stieße. Treffer unter 0,5 mm gelten als Berührung. Beim Motor dauert das rund 0,4 s.
- **Reihenfolge:** Das größte Teil (kein Normteil) bleibt stehen. Runde für Runde kommt heraus, was frei ist. Bei mehreren freien Richtungen gilt nacheinander: bei Normteilen die eigene Achse aus dem Material, dann die Richtung, in der das Teil von etwas abhebt, worauf es liegt, dann die Vorzugsachse, dann weg vom Anker. Ist kein einzelnes Teil frei, kommt eine **Baugruppe** heraus, die nur sich selbst im Weg steht (eine Senke im Blockiergraph, Tarjan), und wird danach genauso in sich zerlegt. Erst wenn auch das nicht geht, muss das Teil mit den wenigsten Hindernissen trotzdem heraus, der Hinweis nennt es.
- **Wer mit wem wandert:** Jedes Teil wandert mit einem Elternteil, das später herauskommt: dem, an dem es aus den meisten Richtungen anliegt. Teile in dieselbe Richtung kommen immer in Frage, solche quer dazu nur, wenn sie es umschließen, entgegenlaufende nie. So wandert eine Schraube mit dem Deckel, eine Mutter mit der Welle, in deren Tasche sie steckt, ein Stößel aber nicht mit dem Nockenrad, auf dem er nur aufsitzt.
- **Lage:** Jedes Teil rückt von seinem Elternteil weg, bis es mit gleicher Lücke (5 % der Modelldiagonale) vor allem liegt, was seine Grundfläche überdeckt, mindestens eine halbe Lücke. Innen zuerst, ein Teil zieht seinen ganzen Teilbaum mit, eine Baugruppe ist dabei ein Block.
- **Normteile und Gewinde:** Die Achse leitet `add_part` aus `direction` ab, der Build legt sie als `axis` in die GLB-Metadaten. Ein Normteil entlang seiner Achse ignoriert, womit es sich überschneidet (Gewinde im Kernloch): Beginnt ein Strahl schon in einem Teil, tritt also beim ersten Treffer aus, überschneiden sich die beiden.
- **Am Motormodell (26 Teile):** Schrauben kommen zuerst entlang ihrer Achse, das Schwungrad nach hinten, Ventile und Stößel nach oben über ihre Führungen, Nockenräder und Kurbelwelle nach vorn. Kolben, Pleuel und Bolzenhülse kommen als Baugruppe nach vorn, darin das Pleuel nach unten aus dem Kolben, die Mutter der Kurbelwange mit der Welle und dann seitlich aus ihrem Schlitz. Nichts steckt fest.
- **Schräge Richtungen (E60):** Der Mesher schreibt zu jeder ebenen Fläche die Normale (nach außen) und zu Zylinder und Kegel die Achse in die Flächendaten. Jedes Teil bringt daraus seine eigenen Richtungen mit: Achsen seiner Zylinder und Kegel, Normalen seiner großen ebenen Flächen (ab 20 % der größten). Die schrägen davon (höchstens 12, die häufigsten) kommen zu den Kandidaten. Ein Teil darf eine schräge Richtung nur nehmen, wenn sie zu seiner Form gehört, sonst schickte die Fase eines Nachbarn es schräg hinaus. Normteile bringen keine Flächenrichtungen mit (ihr Sechskant gäbe nur nutzlose 60°-Richtungen), sie haben ihre Achse. So kommt ein Stift in einer schrägen Bohrung entlang ihrer Achse heraus. Teile, die in verschiedene Richtungen gehen, weichen einander aus, wo sich ihre Hüllquader wirklich überschneiden (der schräge Stift und der Deckel darüber).
- **Schritt für Schritt (E60):** In der Karte Zurück, „Zusammenbauen abspielen“, „Auseinanderbauen abspielen“ (der laufende Knopf hält an), Weiter, ein Tempo von 0,25× bis 2× und die Anzeige „Schritt 3 von 9“, darunter, was in diesem Schritt herauskommt (Nachbesserung nach der Kritik des Nutzers, vorher nur Auseinanderbau und ein fester Takt). Ein Schritt ist eine Runde des Auseinanderbaus, eine Baugruppe zerfällt gleich danach in sich. Jedes Teil geht die Wege seiner Kette (eigener Weg, dann die seiner Eltern), jeden erst, wenn dessen Schritt dran ist: Erst kommen die Schrauben aus dem Deckel, dann hebt der Deckel mit ihnen ab. Am Ende steht die ganze Explosion. Der Schieber verlässt das Abspielen. Der Pfeil rechts fügt die Reihenfolge als Liste in die Eingabe des Agenten ein („1. "Schraube 1" nach +Z; … Zum Zusammenbau rückwärts lesen“). Eine Markierung im Schrittmodus nennt den Schritt.
- **Grenzen:** Der Strahltest arbeitet mit Stichproben und kann sehr dünne Stege übersehen. Montage mit Drehung (Bajonett, Einschrauben) und Bewegungen in mehreren Schritten kennt er nicht. Gruppen aus `group=` spielen keine Rolle mehr, die Baugruppen ergeben sich aus der Geometrie (der Schalter „Gruppen“ aus E57 entfällt).
- **Klicks, Schnitt, Messen:** Auswahl und Hervorhebung arbeiten in der verschobenen Lage, die Hervorhebung wandert mit. Der angeklickte Punkt, den der Agent bekommt, steht in Einbaulage. Der Schnitt schneidet das auseinandergezogene Modell, sein Bereich folgt den Teilen, seine Karte rückt über die der Explosion. Gemessen wird nur in Einbaulage (die exakte Geometrie kennt keine Explosion): „Messen“ setzt das Modell sofort zusammen, „Explosion“ beendet das Messen.
- **Für den Agenten:** Eine Markierung in der Explosion sagt dazu, dass die Teile nur zur Darstellung auseinandergezogen sind und nicht in Einbaulage stehen.
- Die Explosion ändert nichts am Modell, bleibt über neue Builds und Vorschauen erhalten (die Richtungen werden neu bestimmt) und wird nicht gespeichert. Getestet unter Windows.
- **Ladeanzeige (Wunsch des Nutzers, große Baugruppen):** Der Strahltest läuft in Häppchen von 30 ms und gibt dazwischen die Oberfläche frei. Dauert er länger als 0,2 s, deckt eine Ladeanzeige den Viewer ab: „Explosion wird vorbereitet“, Zahl der Bauteile, Fortschrittsbalken, Sekunden, „Abbrechen“ (auch Escape) beendet die Explosion. Die Karte erscheint erst mit dem Ergebnis. Ein neuer Build während der Analyse verwirft sie und beginnt neu.

*Skills (E17, E46, E55; 47 Prüfungen in `app/test/skills.mjs`, 14 Einheitentests):*

- **Panel „Skills“** in der Leiste links: die mitgelieferten Skills mit Kurzbeschreibung, Umschalter für die Stufe und aufklappbar den Themen. Mitgeliefert sind 17 Skills in `app/resources/skills/` (siehe „Skill-Inhalte“ unten, zwei kamen mit E58 dazu, FEM mit E65, Technische Zeichnungen mit E76, Parametrische Modelle mit E77). Inhalt und Kopf (Titel, Beschreibung, Themen, Einstellungen für die Oberfläche) sind auf Englisch, der Kopf war bis E73 deutsch. Die CadQuery-Befehle darin (Kollisionsprüfung, Abstand, Senkungen) sind gegen die Basisumgebung geprüft.
- **Stufen (E55, Wunsch des Nutzers):** Jeder Skill steht je Modell auf **Aus**, **Bei Bedarf** oder **Immer** (Umschalter mit drei Feldern in der Karte, „Immer“ hebt die Karte orange hervor, „Aus“ nimmt sie zurück). Bei Bedarf und Immer kopieren den Skill nach `.soma/skills/<id>.md`, tragen ihn in `project.json` ein (`skills` für Immer wie bisher, `skills_on_demand` für Bei Bedarf, auch in der App-Kopie, E27) und listen ihn im Abschnitt am Ende der `AGENTS.md` (zwischen `<!-- soma:skills -->` und `<!-- /soma:skills -->`, bei älteren Projekten ohne diesen Abschnitt wird er angehängt). Der Abschnitt hat zwei Listen: „Always follow“ (vor jeder Änderung lesen und befolgen) und „Read when relevant“ (je Skill der Anlass aus dem neuen Kopffeld `when`, etwa „Read when the parts will be 3D printed on a filament printer (FDM)“, nicht alle vorab lesen). Die Kopie eines Skills „Bei Bedarf“ hat unter der Überschrift einen Hinweis: dem Skill folgen, solange das Thema gilt, das in `NOTES.md` unter `## Requirements` festhalten (sonst weiß eine spätere Sitzung nichts davon), die Werte sind Standardwerte der App (vom Nutzer eingestellte nennt er mit Namen), also nennen oder nachfragen, und in der App lässt er sich auf „Immer“ stellen. **Aus** entfernt Kopie und Eintrag. Jedes Umstellen zählt als ungespeicherte Änderung und wandert mit Snapshot, Git und ZIP. Ein Wechsel zwischen Bei Bedarf und Immer schreibt die Kopie neu, eine unveränderte ohne Sicherung.
- **Einstellungen (Wunsch des Nutzers):** Ein Skill erklärt im Kopf Variablen, etwa `var overhang: 45 | ° | Max. Überhangwinkel | 10..85` (Standard, Einheit, Bezeichnung, Bereich) oder eine Auswahl `var material: PLA | | Material | PLA, PETG, ABS, ASA, TPU` (Einträge auch als `wert=Anzeige`). Im Text stehen Platzhalter wie `{{overhang}}`. Im Panel stehen die Einstellungen im aufgeklappten Skill: Zahlenfelder (Komma oder Punkt, Enter übernimmt, Escape verwirft) und Auswahllisten, geänderte Werte orange mit Knopf „zurück auf den Standard“, darunter in der Karte „Eingestellt: …“. Die App prüft jeden Wert (Bereich, Auswahl) und lehnt Falsches mit Grund ab. Gespeichert werden nur abweichende Werte, in `project.json` unter `skill_settings`, auch für ausgeschaltete Skills (sie gelten beim Einschalten). Die Kopie im Projekt enthält die eingesetzten Werte, im Text und im Kopf, der Agent liest also konkrete Zahlen. Eine Änderung schreibt die Kopie eines eingeschalteten Skills neu, eine von Hand geänderte Kopie kommt vorher in die Sicherung. Welche Einstellungen die mitgelieferten Skills haben, steht unten. Ein Skill ohne Einstellungen ist erlaubt.
- **Agent:** Ein laufender Agent liest `AGENTS.md` nicht von selbst neu. Die Meldung nach dem Umstellen oder Einstellen sagt das, „An Agent geben“ fügt `[Skill: .soma/skills/<id>.md] ` ein, mit geänderten Einstellungen etwa `[Skill: .soma/skills/3d-druck.md, Einstellungen: Max. Überhangwinkel = 50°] `. `AGENTS.md` erklärt dem Agenten diese Notiz. Den Knopf gibt es bei Bedarf und Immer, bei Bedarf heißt er: jetzt anwenden.
- **Ansehen:** Die Kopie öffnet sich im Code-Panel, nur lesbar („Kopie eines Skills“).
- **Kategorien (E46, Wunsch des Nutzers):** `category` im Kopf ordnet einen Skill unter eine Überschrift im Panel: Arbeitsweise, Fertigungsverfahren, Konstruktionswissen, Prüfen und Zeigen (E58). Eine Kategorie steht dort, wo ihr erster Skill laut `order` steht, Skills ohne Kategorie (etwa aus einer neueren App) unter „Weitere“ am Ende.
- **Skills für neue Modelle (E46, E55, Wunsch des Nutzers):** `default:` im Kopf gibt die Stufe bei neuen Modellen vor (`always`, `on-demand` oder `off`, ohne Angabe Bei Bedarf). Mitgeliefert: Immer für Konstruktionsablauf, Sauber modellieren, Parametrische Modelle (E77) und Normteile (E48), alle übrigen Bei Bedarf. Im aufgeklappten Skill stellt die Auswahl „Stufe bei neuen Modellen“ das für die ganze App um. Gespeichert wird nur, was vom Kopf abweicht, in `state.json` der App-Daten (`skill_defaults`, Einträge von vor E55 mit an/aus gelten als Immer/Bei Bedarf). Das offene Modell bleibt dabei, wie es ist. Ein neues Modell bekommt die Skills vor dem ersten Build, mit Kopie, Eintrag in `project.json` und `AGENTS.md`, also schon im Startcommit, und mit den Standardwerten. Weicht die Vorgabe von „Bei Bedarf“ ab, nennt die Karte sie („Bei neuen Modellen: Immer“). Lässt sich ein Skill nicht kopieren, bleibt er aus, das Anlegen geht weiter.
- **Robustheit (E28):** Nichts wird still ersetzt: Weicht die Kopie im Projekt von der mitgelieferten Fassung ab (vom Agenten geändert, ältere App), meldet die Karte das, und vor dem Überschreiben oder Entfernen kommt sie nach `workspace-backups/<id>-skills/`. Fehlt die Datei eines eingeschalteten Skills, nennt das die Karte und der Projekt-Check, angelegt wird nichts. Fehlt `AGENTS.md`, wird der Skill trotzdem umgestellt, mit Warnung, die Datei wird nicht neu erzeugt. Nennt `AGENTS.md` einen eingeschalteten Skill nicht oder unter der anderen Stufe (etwa nach dem Zurückholen einer alten Fassung), steht das in der Karte. Skills, die nur im Projekt liegen (aus einer neueren App), bleiben gültig.

*Skill-Inhalte (E45):* allgemeine Regeln, kurz gehalten (meist 40 bis 60 Zeilen samt Kopf), damit auch kleinere Modelle sie befolgen. Die Reihenfolge im Panel folgt `order`: Arbeitsweise (1 bis 3), Verfahren (10 bis 14), Konstruktionswissen (20 bis 24), Prüfen und Zeigen (30 bis 31). Den Gehäusebau gibt es nicht mehr (E47). In Projekten, die ihn eingeschaltet haben, bleibt die Kopie gültig, die Karte meldet „Diese App bringt den Skill nicht mit“.

*Normteile (E48, Wunsch des Nutzers; 35 Prüfungen in `app/test/fasteners.mjs`):*

- **Bibliothek `soma.fasteners`:** Schrauben ISO 4762, ISO 7380, ISO 10642, ISO 4017, ISO 4014, DIN 931 und ISO 4026, Muttern ISO 4032, ISO 4033, ISO 4035 und DIN 557, Scheiben ISO 7089, ISO 7091 und ISO 7093, Gewindeeinsätze von ruthex (Standard), CNC Kitchen, McMaster-Carr, Hilitchi und AE-SamZhihui. Vereinfacht ohne Gewinde: Köpfe mit Innensechskant, Sechskant mit 30°-Fase, Schaft mit Fase am Ende. Die Maße kommen aus 13 CSV-Tabellen von bd_warehouse, unverändert in `python/soma/data/fasteners/` mit Lizenz und Herkunftsvermerk (`QUELLE.md`). Gleiche Teile werden einmal gebaut und nur verschoben, 60 Schrauben brauchen deutlich unter einer Sekunde.
- **Lage:** `at` ist der Punkt auf der Achse, an dem das Teil aufliegt (Kopfunterseite, Stirnseite von Mutter und Scheibe, Oberseite bei Senkschraube, Gewindestift und Einsatz). `direction` zeigt von dort ins Material, Standard `-Z`. `at` darf auch eine `cq.Location` oder eine Workplane auf einer Fläche sein, dann gilt deren Normale. `on=teil` sucht die Auflage selbst (Schnitt der Geraden mit dem Teil). `sunk=True` versenkt bündig, `sunk=0.5` tiefer, `angle` dreht um die Achse. `seat`, `outer`, `tip` und `point(d)` sind Punkte auf der Achse, so stapelt der Agent Scheibe und Mutter am anderen Ende.
- **Bohrungen als Werkzeuge für `cut()`:** `clearance_hole(fit, depth, oversize, recess)` nach ISO 273 (fein, mittel, grob), bei versenktem Kopf mit Senkung (Kopf plus Spiel des Lochs), bei Senkschrauben mit 90°-Kegel. `tap_hole()` ist das Kernloch, `HeatSetInsert.hole()` die Bohrung nach der Tabelle, 1 mm tiefer als der Einsatz. `Nut.trap(clearance, slot, slot_length)` ist die Tasche für Sechskant- und Vierkantmuttern, mit Schlitz zum seitlichen Einschieben, so breit wie die Mutter quer zum Schlitz. Alle Werkzeuge ragen 1 mm über die Oberfläche, damit `cut()` keine deckungsgleichen Flächen bekommt.
- **Längen:** nur Normlängen der Tabelle (`lengths()`, `pick_length(min, max)`), sonst ein Fehler mit der Liste. Sonderlängen mit `check_length=False`.
- **Rolle `hardware`:** `add_part` gibt Normteilen ohne Angabe diese Rolle und ihre Farbe (Stahlgrau, Einsätze Messing). Sie stehen deckend bei den eigenen Teilen im Bauteilbaum, die Auswahl zeigt „(Zukaufteil)“, in `output/model.step` stehen sie bei ihrer Gruppe. `soma export --all` überspringt sie und sagt das, einzeln lassen sie sich exportieren. Die App brauchte dafür nur den Zusatz in der Auswahl.
- **Fehler erklärt (Abschnitt 9):** unbekannte Norm mit Liste, alte DIN-Namen mit dem ISO-Nachfolger, fehlende Größe mit den vorhandenen, fehlender Punkt, Gerade ohne Treffer, mehrdeutiger Einsatz. Für die M10-Einsätze nennt die Tabelle als Bohrer „M14“, größer als der Einsatz: `soma` lehnt sie ab, statt eine unbrauchbare Bohrung zu liefern.
- **Für den Agenten (Wunsch des Nutzers):** Die Anleitung steht im Skill „Normteile“, nicht in `AGENTS.md`. Der Skill ist bei neuen Modellen an. Er enthält Beispiel, Lage, Normen, Längen, Mutternfallen, Rolle. Seine Schraubentabelle ist entfallen (nur eine Quelle für die Maße). Der Test führt den Codeblock des Skills aus. „Verbindungen“ nennt `pick_length()`.

*Animation, Analyse, Bilder und Videos (E58, Wunsch des Nutzers; 46 Prüfungen in `app/test/animation.mjs`, 1 Einheitentest):*

- **Grundidee:** Eine Animation ist eine Beschreibung, kein Video. Der Agent schreibt sie in Python in `animations/*.py` mit `soma.anim`: Zeitleiste wie in manim (`play`, `wait`, `run_time`), Drehachsen durch zwei Punkte wie `cq rotate()`, Lagen als `cq.Location`. `soma anim build` führt das Modell aus, dann die Datei (`from model import …` geht, `add_part` bleibt dabei wirkungslos), tastet mit 30 Bildern je Sekunde ab und schreibt eine glTF-Animation nach `.soma/anim/<id>.glb` (je bewegtem Bauteil ein Knoten, Kamera und Zielpunkt, Texte und Zustände in den extras) und `.soma/anim/index.json`. Fehler stehen mit Datei und Zeile im Index.
- **Gelenke, Kamera, Texte:** `hinge` (Drehachse), `slider` (Richtung), `part` (freie Lage), Gelenke auf Gelenken mit `parent=`, ein Gelenk je Teil. Die Kamera kennt die Ansichten des Viewers, `fit` passt Teile über die ganze Bewegung ein, `orbit` kreist um Z, `zoom`. Titelkarten, Untertitel (zum Video auch als WebVTT) und Beschriftungen, die mit ihrem Bauteil wandern. Gemalt werden die Texte auf einer 2D-Fläche über dem Bild, im Viewer wie im Video gleich.
- **Prüfen:** `soma anim info` beschreibt den Ablauf als Text mit Zeiten. `soma anim check` prüft im Abstand von 0,1 s bewegte Teile gegen alle anderen: Überschneidung und Mindestabstand (`--gap`). Seit E64 auf den Dreiecksnetzen, Berührung und Spiel aus der Lage im Modell gelten als gewollt (siehe unten).

*Festigkeit mit FEM (E65, Wunsch des Nutzers; 34 Prüfungen in `app/test/fem.mjs`):*

- **Lastfall:** eine Python-Datei je Lastfall in `analyses/` mit `soma.fem.Study(Titel, material=, safety=, mesh=)`, darin `fix` (auch nur einzelne Achsen), `force` (Gesamtkraft gleichmäßig auf die Flächen), `pressure` (senkrecht, positiv ins Material) und `gravity`. Flächen per CadQuery-Selektor auf dem Teil in seiner Lage im Modell oder mit `near=(x, y, z)`. Werkstoffe wie im Skill „Festigkeit“ oder eigene Werte, `set_material` je Teil. Gedruckte Kunststoffe rechnen mit der Festigkeit quer zu den Schichten.
- **Rechnung:** gmsh vernetzt die BREP-Formen des Builds mit quadratischen Tetraedern auf der echten Geometrie, mehrere Teile werden verschmolzen (fest verbunden, wo sie sich berühren). Die Gesamtsteifigkeit rechnet `fem.py` selbst in numpy (scikit-fem war rund 20-mal langsamer), gelöst wird direkt (bis 12 000 Unbekannte) oder mit pyamg (CG mit algebraischem Mehrgitter, Starrkörperbewegungen als Nahraum). Ein Winkel mit 36 000 Unbekannten braucht rund 5 s Rechnung, dazu der Build. Der Kragbalken trifft die Formel auf 0,2 %.
- **Prüfungen:** Jeder Körper muss gegen alle sechs Starrkörperbewegungen gehalten sein, sonst nennt die Meldung, was frei ist. Lagerkräfte je Einspannung und Gleichgewicht mit den Lasten. Eine zweite Rechnung mit 1,6-fach gröberem Netz, ändert sich die Höchstspannung um mehr als 15 %, sagt ein Hinweis, dass der Wert dort nicht verlässlich ist (scharfe Innenkante), ebenso, wenn die Spitze am Rand einer Einspannung oder Last liegt. Verformung über 5 % der Modellgröße wird gemeldet. Gewählte und im Netz gefundene Fläche werden verglichen.
- **Ergebnis:** wie die anderen Auswertungen `.soma/results/<name>.glb`, Wert ist der Sicherheitsfaktor (Festigkeit durch Vergleichsspannung, kritisch unter dem geforderten, höchstens 99), dazu je Ecke Vergleichsspannung (`_STRESS`) und Verschiebung (`_DISP`), der Lastfall als eigene Netze. Das Netz je Teil ist seine geschlossene Hülle, auch dort, wo es ein anderes Teil berührt (sonst schraffierte der Schnitt alles hinter der Berührfläche), die Kennzahlen gelten für die Außenfläche. Die Spanne reicht bis zum Vierfachen der kleinsten Sicherheit (höchstens das Zehnfache der geforderten), damit ein sicheres Teil nicht ganz grau ist. Die Zusammenfassung nennt Lastfall mit Flächen, je Teil Werkstoff, höchste Spannung, kleinste Sicherheit, größte Verschiebung mit Lage, Problemstellen und die Prüfungen.
- **Im Viewer:** Die Karte „Analyse“ zeigt bei FEM die Verformung überhöht (unverformt, echte Größe oder so, dass die größte Verschiebung 5 % der Modellgröße ist, auf eine runde Zahl), den Lastfall in Blau (Einspannungen kräftig, Lastflächen schwach, Kräfte als Pfeile vor dem Modell, ein- und ausblendbar), Zeilen für Lastfall und Hinweise. Unter dem Zeiger stehen Sicherheit, Spannung und Verschiebung, die Stelle gilt im unverformten Modell. Der Schnitt füllt und umrandet die verformten Netze, die Kontur folgt einer geänderten Überhöhung. „An Agent geben“ nennt alle drei. `soma render --result` zeigt die Verformung wie der Viewer und nennt die Überhöhung in der Legende. Veraltet ist ein Ergebnis auch, wenn die Studie neuer ist, „Neu berechnen“ nimmt die Studie wieder.
- **Farbskala (Wunsch des Nutzers):** Bei FEM wählt man die gezeigte Größe, Sicherheit oder Vergleichsspannung nach von Mises (Grenze ist die zulässige Spannung, Festigkeit durch geforderte Sicherheit, bei mehreren Werkstoffen die des schwächsten, kritisch darüber). Bei jeder Auswertung lässt sich die Spanne der Färbung wählen: automatisch (wie bisher, am Grenzwert ausgerichtet), Min bis Max der Werte im Modell, oder selbst gewählt (zwei Zahlenfelder, gilt beim Tippen, ungültig rot umrandet). Bei Min bis Max und selbst gewählt läuft die Farbe gleichmäßig über die Spanne von Grau bis Rot, die Legende sagt das dazu. Eigene Grenzen bleiben für dasselbe Ergebnis und dieselbe Größe, auch nach „Neu berechnen“. `soma render --result` zeigt weiter die automatische Skala der Sicherheit.
- **Für den Agenten:** Skill „Festigkeit mit FEM“ (Prüfen und Zeigen, bei Bedarf, Einstellung Sicherheitsfaktor), `AGENTS.md` nennt `analyses/` und den Befehl, „Festigkeit“ und „Analyse“ verweisen darauf. Das Beispiel im Skill rechnet im Test so, wie es dasteht.
- **Pakete:** gmsh 4.15 (GPL 2 oder später) und pyamg 5.3 (MIT) in der Basisumgebung, gepinnt in `prototype/phase0/requirements-phase0.txt`. scikit-fem war kurz installiert und ist wieder entfernt. gmsh läuft nur im Python-Prozess von `soma`, nicht in der App. Seit E71 steht SOMA selbst unter GPL-3.0, gmsh passt damit in die Auslieferung.
- **Grenzen:** linear-elastisch, kein Kontakt, kein Gleiten, kein Knicken, keine Vorspannung von Schrauben, keine Ermüdung. Teile sind verschmolzen, nicht gefügt. Werkstoffe gleichmäßig (keine Schichtrichtung, kein Infill, kein Holzfaserverlauf). Werte nur an der Oberfläche. Getestet unter Windows.

*Wartezeiten (E66, Wunsch des Nutzers; Prüfungen in `app/test/versions.mjs` und `unit.mjs`):*

- **Anlass:** Beim Hotwire-Modell (294 Bauteile, davon 164 Normteile, rund 158 000 Dreiecke) dauerten Öffnen, Zurückspringen in der Zeitleiste und ein neues Modell zu lange. Gemessen: Python und cadquery starten 3 s, `model.py` 4,5 s, STEP 1,3 s, Netz, GLB und Geometrie zum Messen 4 s. Er gilt, wenn `.soma/build.json` erfolgreich ist, die Fassung der Ausgaben trägt (`format`, `OUTPUT_FORMAT` in `build.py` und `build.ts`), GLB, Mapping und die Geometrie zum Messen da sind und keine Datei, deren Änderung bei offener App einen Build auslöst (`.py` überall, `inputs/`), neuer ist als der **Start** des Builds. Sonst wird gebaut wie bisher. Die Statusleiste nennt die Zeit des übernommenen Builds.
- **Ein vorgewärmter Python-Prozess für die ganze App** (`soma warm`, `build.ts`): schon beim Start der App, unabhängig vom Projekt, in einem leeren Startordner (`python-start` in den App-Daten, kein Projektordner, den Windows festhielte). Builds und alle `runSoma`-Aufrufe (Vorschau, Export, Animationen, Auswertungen, der Build beim Anlegen) nehmen ihn, danach wärmt der nächste vor. `soma build --wait` entfällt.

Dann legt die App ihn als dessen Vorschau ab (`previews.ts`), ausgelöst von neuen Commits (auch des Agenten) und fertigen Builds. Das Mapping verliert dabei die Code-Verweise (in der Vorschau zeigt der Editor den aktuellen Code), Rollen und Gruppen bleiben. Ändert sich etwas während des Kopierens oder ist die GLB unvollständig, wird verworfen. Stände ohne Cache entstehen wie bisher aus der STEP-Datei, dann im vorgewärmten Prozess.
- **Wiederherstellen:** Die Vorschau bleibt stehen, bis der Build danach fertig ist. Vorher sprang die Ansicht so lange auf den vorherigen Build zurück.
- **Neues Modell:** Der Build vor dem Startcommit läuft im vorgewärmten Prozess, beim Öffnen wird nicht noch einmal gebaut. Der Startcommit wird gleich zur Vorschau.
- **Gemessen mit Hotwire in der App:** Öffnen bzw. App-Start bis zum sichtbaren Modell 1,9 s (vorher rund 13 s), Sprung zu einem Stand im Cache 0,3 s (vorher rund 10 s), ein Stand ohne Cache 8,5 s, neues Modell 3,6 s (vorher rund 8 s, der Rest ist vor allem Git auf dem Netzlaufwerk). Der Build selbst ist unverändert (rund 10 s).

Ein Neustart mit denselben App-Daten fand dann kein Fenster (Debug-Port noch belegt). `harness.mjs` beendet in dem Fall Kinder und Hauptprozess einzeln, wartet auf das Ende und vor dem Start auf einen freien Port.

*Projektumgebung (E25, E67, Wunsch des Nutzers; Prüfungen in `app/test/packages.mjs`):*

- **Anlass:** Bisher landete `pip install` im Terminal nicht in einer Projektumgebung. Auf dem Entwicklungsrechner hatte die Basisumgebung (`venv-full`, mit uv angelegt) gar kein pip, `pip` im Terminal war das globale Python des Rechners.
- **Umgebung je Modell:** `soma env` (`python/soma/env.py`, von der App beim Öffnen gestartet, rund 0,5 s, danach nur, wenn sich die Basis ändert) legt `.soma/env` als venv ohne eigenes pip an, rund 0,6 MB. Eine `.pth`-Datei hängt die site-packages der Basis an, so sieht das Python der Umgebung CadQuery, soma und alle Basispakete, ohne sie zu kopieren. `soma-env.json` hält fest, zu welcher Basis sie gehört (Python, Pfade, Änderungszeit der site-packages). Eine andere Python-Version leert die Umgebung, die App installiert die Liste danach neu.
- **pip:** Die Terminals haben vorn im PATH die Umgebung (`python`), dahinter die Basis (`pip`, `soma`), und `PIP_PYTHON` zeigt auf das Python der Umgebung. Jedes `pip install`, auch `python -m pip`, installiert damit dorthin. Basispakete gelten als vorhanden (pip sieht sie über die `.pth`) und sind in der `pip.ini` der Umgebung über `base-constraints.txt` auf ihre Version festgelegt (als `file:`-URL, weil pip Pfade mit Leerzeichen dort trennen würde). Die Basisumgebung bekommt dafür pip (`requirements-phase0.txt`).
- **soma sieht die Pakete:** `soma` läuft mit dem Python der Basis, auch im vorgewärmten Prozess. Jeder Befehl mit `--project` hängt die site-packages der Projektumgebung hinten an den Suchpfad (`env.activate`), was die Basis hat, gilt also zuerst.
- **requirements.txt:** Nach einem erfolgreichen Build trägt `soma build` die Pakete der Projektumgebung ein, deren Module das Modell geladen hat, mit Version (Kopfzeilen auf Englisch für den Agenten). Ohne Zusatzpakete entsteht keine Datei. Was in der Liste steht, aber nicht installiert ist, bleibt stehen. Die Datei ändert sich nur, wenn sich ihr Inhalt ändert. Der Agent committet sie mit, weil er nach `soma build` committet.
- **Nachinstallieren:** Fehlen beim Öffnen oder nach „Wiederherstellen“ Pakete aus der Liste in der Umgebung (anderer Rechner, alter Stand), installiert die App sie mit pip der Umgebung. Pakete, die die Basis hat, überspringt sie. Builds warten so lange, die Statuszeile zeigt „Installiert Pakete …“ mit den Namen. Scheitert pip (kein Netz, Paket unbekannt), erscheint ein Hinweis mit den letzten Zeilen von pip, gebaut wird trotzdem.
- **Nicht in ZIP und Git:** `.soma/env` steht in der `.gitignore` der Vorlage, bei älteren Projekten in `.git/info/exclude` und bei den Zwischenergebnissen der App (`git.ts`), dazu in den Ausschlüssen der ZIP.

Pfeiltasten und Stepper sammeln kurz. Ein Wert gleich dem im Code entfernt den Eintrag. Ändert der Agent die Datei, baut der Watcher wie bei Code.

Scheitert er vor den Parametern (Syntaxfehler), bleibt die Liste des vorigen Builds mit Hinweis bedienbar.

Neu gerechnet wird nicht von selbst.
- **Grenzen:** Jede Änderung baut das ganze Modell, auch eine reine Stellung wie ein Kurbelwinkel (bei großen Modellen Sekunden). Ein Ergebnis merkt sich nicht, mit welchen Werten es gerechnet wurde. Getestet unter Windows.

*Technische Zeichnungen (E76, Wunsch des Nutzers; Prüfungen in `app/test/drawing.mjs`):*

- **Grundidee:** Der Agent zeichnet selbst, soma liefert Werkzeuge statt automatischer Ansichten und Maße. Eine Zeichnung ist eine Python-Datei `drawings/*.py` mit `soma.drawing.Sheet`, mehrere Blätter je Datei möglich. Wie bei den Animationen bekommt sie das eben gebaute Modell als Modul `model`.
- **Bausteine (`python/soma/drawing.py`):** Blatt A4 bis A0 oder frei, Rahmen und Mittenmarken nach ISO 5457, Schriftfeld nach ISO 7200 (Felder englisch oder deutsch, Symbol der Projektionsmethode 1 oder 3), beides abschaltbar. `view()` projiziert ein Bauteil, eine Gruppe, mehrere, alle oder eine eigene CadQuery-Form in eine der sechs Ansichten, iso oder eine beliebige Richtung, mit eigenem Maßstab, `origin`, `up`, verdeckten Kanten, Tangentenkanten und Stil „phantom“. `section()` schneidet an einer Ebene oder mit einem beliebigen Körper (Halbschnitt, Ausbruch) und schraffiert die Schnittflächen je Teil im Wechsel 45/135°, Teile in `unhatched` bleiben ungeschnitten, mit `parent` entsteht der Schnittverlauf mit Pfeilen und Buchstaben. `section(path=[...])` schneidet entlang eines geknickten Schnittverlaufs (Stufen- oder Halbschnitt) und zeichnet ihn mit dicken Enden und Knicken. Wo ein Schnitt nur von der Seite zu sehen ist (Stufe, Mitte des Halbschnitts, Rand eines Ausbruchs), fällt die Kante weg (ISO 128-44). `breaks=[(p1, p2)]` kürzt `view()` und `section()` um den Teil zwischen zwei Modellpunkten, mit Bruchlinien (schmale Zickzacklinie, 6 mm Lücke), Maße darüber zeigen die volle Länge. `detail()` schneidet einen Kreis aus einer Ansicht und vergrößert ihn. Ansichtstitel, Schnitt- und Einzelheitsbuchstaben lassen sich mit `label_at`, `letters_at` und `letter_at` verschieben. Maße an Modellpunkten (`dim` waagerecht, senkrecht, schräg, `diameter`, `radius`, `angle`), Werte immer gemessen, `<>` für den Messwert im Text, Toleranzen. Dazu Mittellinien, Mittenkreuze, Hinweislinien, Texte, Tabellen und `sh.msp` für alles Weitere direkt mit ezdxf.
- **Technik:** verdeckte Kanten mit `HLRBRep_Algo` aus OCP (Kanten bekommen danach 3D-Kurven, sonst stürzen die Booleschen Operationen der Einzelheit ab), Kanten als LINE, ARC, CIRCLE, ELLIPSE oder Polylinie, echte DIMENSION-Objekte mit `dimlfac`, Layer und Linienarten nach ISO 128. PDF und PNG entstehen aus derselben DXF über das Zeichenmodul von ezdxf mit matplotlib, keine neuen Pakete. Schrift DejaVu Sans (liegt matplotlib bei). Zwei Fehler von ezdxf umgangen: Das Ø wurde in jeder Schrift zum Fleck (Löcher in Zeichen über Verschachtelung gesucht, für Text jetzt mit der Füllregel der Schrift), und Schraffurlinien bekamen einen Zufallsversatz (fester Startwert).
- **Bytegleich:** Gleiche Zeichnung, gleiche Dateien (DXF mit festen Zeitstempeln und sortierten Klassen, PDF ohne Erstellungsdatum). Ein Neubau ohne Änderung ändert nichts im Verlauf. Das Datum im Schriftfeld ist der Tag des Baus, wenn der Agent keines angibt.
- **Prüfung (meldet nur, E28):** Text außerhalb des Rahmens oder auf dem Schriftfeld, Ansichten übereinander, Texte und Maßzahlen übereinander, Texte auf Kanten, Maßpunkte auf keiner Kante (mit Hinweis auf gerundete Ecken) oder nur auf verdeckten, Durchmesser ohne passenden Kreis, getippte Zahlen, die vom Messwert abweichen, Text unter 2.5 mm, Maßstab nicht nach ISO 5455, leeres Blatt. Seit dem ersten Agent-Test auch Texte auf Maß-, Hinweis-, Mittel-, Bruch- und Schnittlinien, Ansichten, Texte und Hinweislinien auf einer Tabelle (Stückliste), Texte, die nicht in ihre Zelle oder ihr Feld im Schriftfeld passen. Texte zählen als gedrehte Rechtecke (schräge Maßzahlen meldeten vorher Kanten neben sich). Maße dürfen auf Mittenkreuzen und Mittellinien des Agenten enden (Positionen, die nicht im Modell sind). Meldungen zu Beschriftungen von soma nennen den Parameter zum Verschieben.
- **Befehle:** `soma drawing build [Datei]` schreibt `output/drawings/<Name>.pdf` und `.dxf` (im Verlauf und in der ZIP wie `output/model.step`) und ein Bild `.soma/drawings/<Name>.png` mit 200 dpi (längste Seite höchstens 7000 px, nicht in Verlauf und ZIP). Fehler mit Datei und Zeile, Hinweise mit Zeile. `soma drawing list` mit „veraltet“, `soma drawing info` beschreibt Ansichten mit Lage auf dem Blatt, Kreise und Bögen je Ansicht und alle Maße mit Wert. PDF und DXF entfernter Blätter bleiben liegen, die Ausgabe nennt sie. Alle Blätter zusammen stehen in `output/drawings.pdf` (nach Datei, dann Reihenfolge darin), Blätter, die nicht neu gebaut wurden, kommen dafür aus ihrer DXF. Hat eine Zeichnung Fehler, bleibt diese Datei unverändert (sonst fehlte still ein Blatt), die Ausgabe sagt es.
- **Erster Agent-Test (2026-10-09):** Rückmeldungen des Agenten, alle behoben: `num(130, 0)` ergab „13“, `diameter()` mit `text="Ø<> H7"` ergab „ØØ8“ (Ø und R vor `<>` werden jetzt nicht verdoppelt), der Text eines Durchmessers lag gegenüber von `angle` (jetzt wie beim Radius die Richtung von der Mitte zum Text), mehrzeiliger Text verlor Einrückungen und wurde fälschlich als 161 mm außerhalb gemeldet (ezdxf misst MTEXT mit Umbrüchen, die beim Zeichnen nicht entstehen, jetzt eine TEXT-Zeile je Zeile), ein zu langer Werkstoff im Schriftfeld, Positionsnummern auf der Stückliste und Beschriftungen auf Maßen wurden nicht gemeldet und Beschriftungen ließen sich nicht verschieben. Gewünscht und ergänzt: Bruchlinien, Schnittverlauf bei Stufenschnitten, eine Gesamt-PDF, Maße zu Positionen ohne Geometrie. Dabei gefunden: Wurde in einem Skript Text gemessen, bevor DejaVu Sans angemeldet war (etwa über `leader()`), blieb für den ganzen Lauf eine Ersatzschrift hängen, auch in der PDF. Die Schrift wird jetzt beim Anlegen des Blatts angemeldet.
- **Für den Agenten:** Skill „Technical drawings“ (`zeichnung.md`, Prüfen und Zeigen, bei Bedarf) mit Best Practices nach ISO 128, 129, 5455, 5456, 7200 und den Werkzeugen, Einstellungen Norm, Blattgröße, Allgemeintoleranz und Sprache. `AGENTS.md` nennt `drawings/` und den Befehl. Der Nutzer öffnet die PDF in der vorhandenen PDF-Ansicht und kann Seiten markieren.
- **Grenzen:** Ein Agent-Test (Claude Code, ein Blatt). Text steht in der PDF als Pfad, „Zitat an Agent“ geht dort nicht. Keine automatische Stückliste (Daten muss der Agent zusammenstellen), keine Gewindedarstellung nach ISO 6410 (Normteile haben kein Gewinde), keine Rasterfelder am Rahmen, kein Eintrag im Umschalter des Viewers. Gedrehte Schnitte (Schnittverlauf mit schrägem Abschnitt) werden nicht in die Ebene geklappt, ihre schrägen Flächen bleiben ohne Schraffur. Die Projektion großer Baugruppen ist ungetestet. Getestet unter Windows.

*DXF-Ansicht (E80, Wunsch des Nutzers; 23 Prüfungen in `app/test/dxf.mjs`):*

- **Öffnen:** Klick auf eine `.dxf` im Dateibaum, „Open“ im Kontextmenü oder ein Link in einer Markdown-Datei öffnet sie als Reiter im Code-Panel wie eine PDF, nur zum Lesen. Vorher kam nur der Hinweis, dass die App keine Ansicht dafür hat.
- **Zeichnen (`python/soma/dxfview.py`, `app/src/main/dxf.ts`):** `soma dxfview <datei> --out <json>` (versteckt, nur für die App, über den vorgewärmten Python-Prozess) liest mit `ezdxf.recover` und zeichnet mit dem Zeichenmodul von ezdxf, demselben wie für PDF und Bild der technischen Zeichnungen (E76): Linientypen als Striche, Schraffuren, Maße, Texte in der Schrift der Zeichnungen, Blöcke, Splines, Ellipsen, Bilder als Rahmen. Heraus kommen Stapel je Art (Linie, Fläche, Text, Punkt), Layer, Farbe und Strichstärke mit Pfadbefehlen M, L, Q, C, Z. Bögen und Schrift bleiben Kurven und sind bei jedem Zoom glatt. Die Koordinaten sind relativ zur Mitte und auf rund sieben Stellen gerundet, so reichen 32 Bit auch weit vom Ursprung. Der Renderer baut daraus `Path2D` und zeichnet auf einer Canvas (`app/src/renderer/dxfview.ts`). Ein A3-Blatt mit 744 Objekten braucht rund 1 s, direkt nach einem anderen Auftrag der App bis zu 4 s (der nächste vorgewärmte Prozess lädt noch cadquery).

Die Leiste zeigt die Größe mit Einheit (`$INSUNITS`) und die Koordinaten unter dem Zeiger auf einen Bildpunkt genau. Dunkler Grund wie im Modellbereich eines CAD-Programms, ezdxf macht Farbe 7 deshalb hell. Strichstärken in Bildschirmpunkten unabhängig vom Zoom (0,25 mm 1 px, höchstens 6 px), auf Papier skaliert würden sie beim Hineinzoomen die Details verdecken.
- **Layer:** Menü „Layers“ mit Farbe und Haken je Layer und „Show all“. In der Datei aus- oder eingefrorene Layer zeichnet soma trotzdem, die Ansicht blendet sie zunächst aus und kennzeichnet sie („off in file“). Solange etwas ausgeblendet ist, zeigt der Knopf „Layers 4/5“.
- **Für den Agenten:** „Mark up view“ legt die Ansicht in doppelter Auflösung auf die Zeichenfläche der Markierung. Ist nur ein Ausschnitt zu sehen, nennt die Notiz ihn in Koordinaten der Datei (`[Markup: …, drawn on cut/plate.dxf, area x 73.33 to 126.67, y 2.95 to 81.67 mm]`).
- **Von außen geändert:** Nach jeder Dateiänderung fragt die Ansicht mit dem Fingerabdruck (Größe, Änderungszeit) nach, gezeichnet wird nur bei einer neuen Fassung. Ausschnitt (in Koordinaten der Datei) und Layerwahl bleiben, eine eingepasste Ansicht passt neu ein. Ist die Datei weg, geht der Reiter zu. Laufende Aufträge werden nicht verdoppelt.
- **Melden statt reparieren (E28):** Beschädigte Dateien liest `ezdxf.recover` so weit wie möglich, die Ansicht nennt die Zahl der Probleme, die Datei bleibt unverändert. Was ezdxf nicht zeichnen kann (etwa 3D-Körper ohne Ersatzgrafik), nennt ein Hinweis („Not shown: 1 × 3DSOLID“), unsichtbare Objekte und zu kleiner Text nicht. Keine DXF: Meldung in der Ansicht. Ist der Modellbereich leer, zeigt sie den ersten Papierbereich mit Inhalt und sagt es. Dateien über 200 MB lehnt sie ab, über 6 Millionen Zahlen zeichnet sie nur einen Teil, beides mit Hinweis.
- **Grenzen:** Nur ansehen, kein Messen, Auswählen oder Bearbeiten, keine Wahl zwischen Papierbereichen, keine DWG. Große Dateien (Zehntausende Objekte) nicht gemessen. Getestet unter Windows.

*Einstellungen: Viewer, Speicher, Info (E81, Wunsch des Nutzers; 45 Prüfungen in `app/test/settings.mjs`, 6 in `app/test/unit.mjs`):*

- **Orthografisch:** Eine zweite Kamera. Beim Umschalten bleiben Blickrichtung, Drehpunkt und die Bildhöhe in der Ebene des Drehpunkts (Maßstab aus dem Abstand und 35°), das Bild springt nicht. - **Storage (`app/src/main/storage.ts`):** Größe der App-Daten insgesamt und je Bereich: Modelle (Arbeitsordner mit Zahl), Sicherungen, Vorschau-Cache, Bilder der Startseite, eigene Skills, Übriges (Caches von Chromium, `state.json`, `settings.json`). Verknüpfungen zählen nicht. Je Bereich ein Knopf, der den Ordner öffnet (der Renderer nennt nur die Kennung des Bereichs, nie einen Pfad). **Zu klären**

- **Namen:** Notizdatei `NOTES.md`, Ordner `exports/` (Ort, getrackt oder nicht)
- **Lizenzen der Komponenten:** Hinweise und Texte aller mitgelieferten Teile (Git, Python-Pakete, gmsh, pdf.js, IBM Plex, Tabellen aus bd_warehouse) für den Installer sammeln. Die Lizenz von SOMA selbst ist entschieden (GPL-3.0, E71)
- **Mittelbereich:** Tab-Umschaltung oder geteilte Ansicht zwischen Viewer und Sketch (E15)
- **Build:** Auto-Build standardmäßig an oder aus, Statusanzeige, Fehlerpanel, Verhalten bei erneuter Änderung während des Builds (E20)
- **Speichern/Öffnen:** mehrere Projekte parallel (bisher eines pro Fenster), Aufräumen alter Workspaces und Sicherungen, ZIP auf Netzlaufwerk (Speichern dorthin geht, Verhalten bei Verbindungsverlust ungetestet), ZIP-Größe bei langen Verläufen (seit E75 gepackt, jede STEP-Fassung bleibt aber im Verlauf) und vielen Markierungen (je Bild einige hundert KB) (E21)
- **Git:** Einbettung und Updates des Git-Binaries (E31), Verhalten bei sehr langen Verläufen (die Leiste zeigt bisher bis zu 500 Stände), Umschreiben des Verlaufs durch den Agenten trotz Verbot (die Leiste bleibt tolerant, es gibt nur eine Meldung bei fehlendem Repository, losem HEAD oder anderem Branch)
- **Pakete (E25, E67):** Ohne Internet scheitert das Nachinstallieren mit Hinweis, einen eigenen Paketcache gibt es nicht (pip nutzt seinen eigenen). `uv pip install` sieht die Basispakete nicht und ignoriert die `pip.ini`, es würde z. B. numpy doppelt installieren. Ein Panel „Pakete“ fehlt noch (die Liste steht in `requirements.txt`). Für die Auslieferung: Basisumgebung mit pip, eigenständiges Python statt venv (dann ginge auch `--system-site-packages` statt der `.pth`). Getestet nur unter Windows

- **Echte Fremddateien:** Herstellerplatinen und große Baugruppen mit Stückliste in Phase 1 testen
- **Netzlaufwerke (Windows):** Liegt das Programm auf einem Netzlaufwerk, starten die sandboxed Prozesse von Electron nicht. Die installierte App muss lokal liegen, Fehlermeldung ist vorhanden. Klären, wie der Installer damit umgeht und ob Firmenrechner mit umgeleiteten Profilen Probleme machen
- **Updates:** Regeln für alte und neuere `api_version`, Auto-Update der App, Signierung (E36)
- **Format** von `model.map.json` (Entwurf `version 0` aus Phase 0 steht) und der Ausgabe von `soma check`
- **Vorschau-Cache (E66):** wächst unbegrenzt (Hotwire rund 13 MB je Stand), es gibt kein automatisches Aufräumen, seit E81 nur das Leeren von Hand in den Einstellungen. Vorschlag: älteste Stände je Projekt über einer Grenze löschen, sie entstehen bei Bedarf neu
- **Weitere Beschleunigung (gemessen, nicht umgesetzt, E66):** Der Mesher liest jede Form einzeln aus, auch gleiche: Die 164 Normteile im Hotwire sind nur 17 verschiedene Formen (rund 1,5 s zu sparen). Das Auslesen in Python dauert rund 3 s gegen 0,6 s Vernetzung in OCC, über VTK aus CadQuery wären es rund 1,2 s für alles (größerer Umbau, Flächen- und Kanten-IDs fürs Messen). GLB erst schreiben und melden, STEP und Geometrie danach (1,9 s früher im Viewer). Hinweise im Skill „CadQuery“: Bohrungen in einem `cut` abziehen (20 Bohrungen 0,15 statt 0,75 s), gleiche Teile mit `.moved()` platzieren statt neu bauen (auch Netz und STEP profitieren). Weniger Git-Aufrufe beim Anlegen und Wiederherstellen (je rund 0,15 s auf dem Netzlaufwerk). Den Messdienst aus dem vorgewärmten Prozess starten
- **Toleranz des Meshers:** Feste 0,05 mm passt für kleine Teile, große brauchen eine an der Größe orientierte Toleranz (siehe Leistungsmessung)
- **Auswahlen des Agenten:** Flächen-IDs gelten nur pro Build, Verweise brauchen Bauteilname plus Geometrieangabe
- **Inhalte** von `AGENTS.md` und den Skills, mit einem echten Agenten zu testen. Vor allem (E55): Liest ein Agent einen Skill „Bei Bedarf“ von selbst, wenn das Gespräch das Thema wechselt (etwa „jetzt für den 3D-Druck“), und hält er das in `NOTES.md` fest? ## 12. Größte Risiken

| Risiko | Warum | Gegenmaßnahme |
|---|---|---|
| STEP-Namen mit CadQuery | **Erledigt in Phase 0:** Namen, Farben, Alpha bleiben erhalten. Nicht-ASCII-Namen werden zerstört | ASCII-Namen in der STEP, Anzeigename in `model.map.json` |
| Codequalität der Agenten mit CadQuery | Verkettete API mit verstecktem Zustand, halluzinierte Aufrufe | Strikte Idiome in `AGENTS.md`, Beispiele, Feedback-Loop (bauen, messen, rendern) |
| Agenten ignorieren die Konventionen | Nicht jeder Agent folgt `AGENTS.md` oder Verweisen | Robustheit (Abschnitt 9), Agent-Test in Phase 1 |
| Klick auf Fläche und Code | Kein Framework liefert Flächen-IDs oder Zeilenbezug | **In Phase 0 bestätigt** mit eigenem Mesher und Hilfsbibliothek. Verknüpft wird der `add_part`-Aufruf (E10), nicht die Entstehungszeile der Fläche |
| Installationsgröße und Einbettung | **Gemessen:** OCP hängt hart an VTK, installiert 0,76 bis 1,04 GB | Vorerst hingenommen (E37). Später: Casadi und VTK-Teilmenge prüfen, Komprimierung |
| Nur Windows getestet | Bundling und Bibliotheken auf macOS und Linux ungeprüft, E2 verlangt alle drei | Früh in Phase 1 auf macOS und Linux nachziehen |
| Modellgröße und Buildzeit | Große Teile brauchen 8 bis 10 s (Meshen in OCC), feine Toleranz bis 30 s | Auto-Build abschaltbar (E20), Toleranz nach Bauteilgröße |
| Chats bei ZIP-Weitergabe | Agenten speichern Historie außerhalb des Projekts | Bewusst akzeptiert (E5) |
| Git für Nicht-Programmierer | Agent und App teilen sich ein Repo | Nur Vorschau und Wiederherstellen als neuer Commit (E35), App-Schreibvorgänge serialisiert, Sicherung vor Wiederherstellung. **Umgesetzt und getestet**, Claude Code committet laut erstem Test selbst. Lange Sitzungen und andere Agenten sind ungeprüft |
